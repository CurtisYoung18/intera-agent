## Loop & Engine 运作机制速览

```
用户消息 → POST /api/messages
  → Hub Routing (跳过新 caseId)
  → AgentLoop.run()
    ├─ 上下文压缩 (token 阈值检查)
    ├─ buildStagePrompt() — 注入 current stage / required skills / evidence
    ├─ filterTools() — 白名单过滤 (nudge≥2 时强制仅 missing skills)
    ├─ LLM stream (core llm)
    │   ├─ text_delta → 前端流式渲染
    │   ├─ tool_use → preTool policy check
    │   │   ├─ blocked → policy_blocked SSE (红点 bubble, continue loop)
    │   │   └─ passed → executeHttp/mock (绿点 executing → completed)
    │   └─ end_turn → 检查 stage 要求
    ├─ 无 tool 调用时:
    │   ├─ checkRequiredSkills() + checkEvidenceRequirements()
    │   ├─ 未满足 → nudge (最多 3 次 → escalated + 黄点 bubble)
    │   └─ 已满足 → evaluateTransition() → 进入下一 stage
    ├─ 有 tool 调用时:
    │   ├─ postTool policy (批量 LLM)
    │   ├─ 终端 tool 处理 (create_case, finalize_case, create_human_task)
    │   └─ nudgeCount 重置为 0
    └─ finalize_case:
        ├─ requireHumanReview? → 检查 create_human_task 是否已调用
        ├─ preFinalize policy (evidence_required, no_compensation, must_cite)
        └─ passed → case resolved, loop 结束
```

### Nudge 机制

| Nudge | 文本 | filterTools 行为 |
|-------|------|-----------------|
| 1 | "Stage expects: X, Y. Please call these tools." | 全部 availableSkills |
| 2 | "STOP generating text. Call tools NOW." | **强制仅返回 missing required skills** |
| 3 | "FINAL WARNING. Call NOW: X, Y." | 强制仅返回 missing required skills → 仍不调 → escalated |

### Policy Engine

| Hook | 触发时机 | Block 行为 |
|------|---------|-----------|
| preTool | tool_use 执行前 | 红点 bubble + [POLICY] 注入 + continue loop |
| postTool | 所有 tool 执行后 | 批量 LLM 评估冲突 → escalated + 黄点 bubble |
| preFinalize | finalize_case 前 | [POLICY] 注入 + continue loop |

### requireHumanReview

| Case Type | 值 | finalize 前要求 |
|-----------|-----|----------------|
| deposit_issue | true | create_human_task 必须已被调用 |
| refund_request | true | create_human_task 必须已被调用 |
| withdrawal_issue | true | create_human_task 必须已被调用 |
| account_issue | false | 无强制要求 |
| order_issue | false | 无强制要求 |
| promotion_inquiry | false | 无强制要求 |

## Case Type 1: deposit_issue `💰` 存款未到账

**场景**: 用户充值后余额未增加，怀疑漏单。

### 正常 Flow

```
User: "我刚刚充了500，支付宝扣钱了但余额没变"
  → Agent: 安抚 + create_case(deposit_issue, "用户反映支付宝充值500未到账")
  → ● create case (绿点, completed)
  → Stage: created → evaluating

User: (无需输入 — created stage 检查 confirmedFacts)
  → 缺少 txnId/amount/paymentMethod → transition to collecting
  → Stage: collecting
  → Agent: 调用 request_user_input
  → 前端渲染表单卡片: [交易流水号] [充值金额] [支付方式] [日期(选填)]

User: 填写表单 → 提交
  → confirmedFacts: { txnId: "TX123", amount: "500", paymentMethod: "alipay" }
  → all_evidence_gathered → transition to investigating
  → Stage: investigating
  → Sub-agent dispatch: transaction_verifier + history_reviewer (并行)
  → ● query_order_status (绿点, completed, 可展开看 result)
  → ● query_payment_channel_status (绿点, completed, 可展开看 result)
  → Agent: "订单状态显示已完成，渠道正常。您的充值已到账，可能是余额显示延迟。"
  → evaluation: 证据支持结案 → resolved
  → Agent: 调用 finalize_case
  → requireHumanReview=true → 检查 create_human_task 未调用
  → ● Blocked finalize_case — mandatory_human_review (红点)
  → Agent: [POLICY] → 调用 create_human_task
  → Case 进入 escalated 状态 → 人工处理
```

### 可能错误 & 纠偏

| 错误 | 表现 | 原因 | 纠偏 |
|------|------|------|------|
| Agent 不调 create_case | 纯文本回复 "请提供流水号" | 系统 prompt 不够强 | created stage 有 request_user_input，模型会调 |
| collecting 阶段不调 request_user_input | Agent 文本列出字段 "请告诉我txnId、金额..." | 模型忽略 stage 要求 | Nudge 1 → 提示调 request_user_input |
| 持续不调 | Nudge 2 → 强制 tools 只剩 request_user_input | 硬约束 | 模型只能调 request_user_input |
| investigating 阶段数据冲突 | Agent 说 "系统显示已完成" 但用户坚持未到账 | postTool conflict_requires_human 触发 | [POLICY] → Agent 调 create_human_task |
| finalize 被 mandatory_human_review 拦截 | 红点 bubble | requireHumanReview=true | Agent 必须先调 create_human_task |

### 验证要点

1. created → collecting 自动转换（缺少 txnId 时）
2. collecting 表单 key 必须为 txnId/amount/paymentMethod（非其他命名）
3. sub-agent 并行执行（绿点同时出现）
4. tool result 可展开查看真实 API 数据
5. finalize 前必须经过 human review（deposit_issue 强制）

## Case Type 2: account_issue `🔒` 账号问题

**场景**: 用户无法登录，怀疑账号被盗/被冻结。

### 正常 Flow

```
User: "我的账号登不上去，提示异常"
  → Agent: 安抚 + create_case(account_issue, "用户反映账号登录异常")
  → ● create case (绿点, completed)
  → Stage: created → 检查 confirmedFacts → 缺 userId/issueType → collecting

User: 填写表单 { issueType: "登录异常", symptoms: "提示账号风险" }
  → confirmedFacts: { userId: "JAYA113C88F", issueType: "登录异常", symptoms: "提示账号风险" }
  → all_evidence_gathered → investigating

Agent (investigating):
  → Sub-agents: account_platform_checker (get_account_status + get_kyc_status)
                account_history_policy (read_case_history + kb_hybrid_retrieve)
  → ● get_account_status (绿点) → 展开: {"data":{"status":"Active"}}
  → ● get_kyc_status (绿点) → 展开: {"data":{"kyc_status":"pending_submit"}}
  → ● read_case_history (绿点) → 展开: mock 3条历史工单
  → Agent: "账号状态正常(Active)，KYC待提交。历史工单3条均已解决。
           系统未检测到异常，建议您完成KYC验证后重试。"
  → evaluation: 证据充分 → resolved
  → Agent: finalize_case (requireHumanReview=false, 直接通过)
  → ● finalize case (绿点) → Case resolved
```

### 可能错误 & 纠偏

| 错误 | 表现 | 原因 | 纠偏 |
|------|------|------|------|
| Agent 只调 get_account_status，不调 get_kyc_status | 仅显示账号状态，缺 KYC 信息 | 模型认为一个 API 就够了 | Nudge 1 → "Stage expects: get_kyc_status, read_case_history" |
| Nudge 后仍不调 | Nudge 2 → 硬约束，只显示 get_kyc_status + read_case_history | 模型无其他工具可选 | 强制调用 |
| KYC 返回 "pending_submit" + 账号 Active | Agent 直接 finalize | 无冲突，正常 | 正确行为 |
| 账号被锁 (status: "locked") + 用户说登不上 | 系统与用户一致 | 无冲突 → resolved | 正确，告知用户解锁流程 |
| 账号 Active + 用户说登不上 | postTool conflict_requires_human 触发 | 数据矛盾 | [POLICY] → Agent 调 create_human_task |
| read_case_history 返回多次账号问题 | Agent 应发现模式 | 证据充足 → resolved | 正确 |

### 验证要点

1. collecting 表单字段 key 为 userId/issueType/symptoms（session 已提供 member_id）
2. get_account_status 和 get_kyc_status 返回真实的 HTTP API 数据（非 mock）
3. read_case_history 返回 mock 数据（无真实 API）
4. KYC pending 不应触发 conflict（系统数据与用户说法一致）
5. 无 requireHumanReview → finalize 直接通过

## Case Type 3: withdrawal_issue `💸` 提现问题

**场景**: 用户提现未到账或提示打码量不足。

### 正常 Flow

```
User: "我提现了1000，两天了还没到账"
  → Agent: 安抚 + create_case(withdrawal_issue, "用户反映提现1000未到账")
  → ● create case
  → Stage: created → evaluating → collecting

User: 填写表单 { issueType: "提现未到账", amount: "1000" }
  → all_evidence_gathered → investigating

Agent (investigating):
  → Sub-agents: withdrawal_verifier (get_latest_withdrawal + get_withdraw_conditions)
                history_reviewer (get_transaction_history + read_case_history)
  → ● get_latest_withdrawal → 展开: {"status":"pending","created_at":"...","time_passed":172800}
  → ● get_withdraw_conditions → 展开: {"data":[...]}
  → Agent: "您的最新提现申请状态为pending，已过48小时。打码量条件显示..."
  → evaluation: 数据明确 → resolved
  → Agent: finalize_case
  → requireHumanReview=true → 红点 Blocked
  → Agent: create_human_task → 人工审核
```

### 验证要点

1. get_latest_withdrawal 返回真实数据（含 time_passed 字段）
2. get_withdraw_conditions 返回真实打码量数据
3. requireHumanReview=true → finalize 前必须人工

## Case Type 6: refund_request `↩️` 退款申请

**场景**: 用户要求退款。

**注意**: 当前 stage config 存在不一致 — `stages` 声明了 `collecting` 但实际配置为 `approved` 而非 `collecting`。

### 正常 Flow

```
User: "我要退款，订单 #ORD456，金额200，质量有问题"
  → Agent: create_case(refund_request, "用户申请退款订单ORD456")
  → ● create case
  → Stage: created → auto transition → reviewing

Agent (reviewing):
  → ● query_order_status(txnId="ORD456") → 展开 mock
  → Agent: "订单ORD456确认可退款，金额200"
  → evaluation: eligible → approved

Agent (approved):
  → finalize_case
  → requireHumanReview=true → 红点 Blocked
  → Agent: create_human_task → 人工审批退款
```

### 验证要点

1. refund_request 有独立的 approved stage（非 resolved）
2. requireHumanReview=true → 退款必须人工审批
