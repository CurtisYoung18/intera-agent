## 二、知识检索（Retrieval）策略：从 Mock 到生产级 Hybrid RAG

### 2.1 现状

- `kb_hybrid_retrieve` 在 `skills.ts:522` 是 **mock**，固定返回 3 条与"deposit delay"相关的 demo 文章。
- 系统设计上把 KB 调用归入了普通 `Skill`（与查订单等同等地位），由 LLM 自主决定何时调用，结果 merge 到 `CaseMemory.skillResults`。
- 商户已有"基于 RAG 的 Q&A 产品"，本平台只需通过 API 调用即可。

### 2.2 生产化目标

> KB 检索不是为了"拼答案给用户"，而是为 Agent 提供**可引用、可验证、可行动**的证据。

#### 三种独立但可组合的检索策略

| 策略 | 用途 | 触发时机 | 输出对 Agent 的价值 |
|------|------|----------|---------------------|
| **A. 商户 RAG API 直连** | 调用商户既有 RAG 产品（最快上线） | LLM 自主调用 `kb_hybrid_retrieve` | 拿到候选文档 chunks + relevance score |
| **B. Intera-native Hybrid Retrieval** | 我们自建的检索层，支持商户上传任意来源 | 同上 | 比商户 RAG 更精准（针对客服场景做了优化） |
| **C. Contextual Retrieval（Anthropic 模式）** | 对 chunk 加上上下文前缀后再 embed | 入库时离线处理；检索时无差别 | 显著降低 chunk 切碎导致的语义丢失 |

#### 2.3 具体落地路径

##### 路径 A（最快上线 · 1-2 周）：商户 RAG 直连

在 Console → Skills 里把 `kb_hybrid_retrieve` 改成 `mode: 'http'`：

```json
{
  "name": "kb_hybrid_retrieve",
  "mode": "http",
  "endpoint": "https://商户域名/api/rag/search",
  "httpMethod": "POST",
  "headers": { "X-API-Key": "${RAG_KEY}" },
  "timeoutMs": 5000
}
```

**需要在 Console 补的能力**：
- Skill 配置里支持 `${ENV_VAR}` 占位符（避免明文 key 进 DB）
- 在 `streaming-tool-executor.ts` 的 `executeHttp` 加上 `Authorization` / `apiKey` / `X-API-Key` 多种认证方式适配
- HTTP 失败重试（指数退避，最多 3 次）

##### 路径 B（深度优化 · 6-8 周）：Intera-native Hybrid

新增 DB 表：

```prisma
model KnowledgeDoc {
  id          String   @id @default(cuid())
  customerId  String
  source      String   // help_center / faq / promo_terms / sop_doc
  url         String?
  title       String
  rawContent  String   @db.Text
  locale      String   @default("zh-CN")
  tags        String   // JSON: string[]
  caseTypeTag String?  // 可关联到 deposit_issue 等
  enabled     Boolean  @default(true)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  chunks      KnowledgeChunk[]
  @@index([customerId, source])
}

model KnowledgeChunk {
  id           String   @id @default(cuid())
  docId        String
  doc          KnowledgeDoc @relation(fields: [docId], references: [id], onDelete: Cascade)
  ordinal      Int      // 0-indexed 顺序
  text         String   @db.Text
  contextPrefix String? @db.Text  // ★ Contextual Retrieval：LLM 生成的"该 chunk 在文档中的位置/角色"
  tokenCount   Int
  // pgvector 字段（用 Unsupported 类型 + raw SQL 索引）
  embedding    Unsupported("vector(1536)")?
  bm25Vec      Unsupported("tsvector")?
  @@index([docId, ordinal])
}

model KnowledgeIngestJob {
  id          String   @id @default(cuid())
  customerId  String
  source      String   // upload / sync_url / crawl
  status      String   @default("pending") // pending|running|completed|failed
  payload     String?  @db.Text  // 上传文件路径 / URL / 配置
  totalDocs   Int      @default(0)
  processedDocs Int    @default(0)
  errors      String?  @db.Text  // JSON: [{docId, error}]
  startedAt   DateTime?
  finishedAt  DateTime?
  createdAt   DateTime @default(now())
}
```

**Console 新增 "Knowledge Base" 页面**（建议放在 admin 侧栏第 6 项）：
- 上传文档（Markdown / PDF / docx / URL 导入）
- 触发 Contextual Retrieval 离线处理（每个 chunk 让 Haiku 生成 50 词上下文前缀，缓存 90% 的 prompt 共享部分）
- 查看 chunk 列表、覆盖率仪表盘
- 召回测试台（输入 query 实时看 BM25/Vector/Rerank 三路结果对比）

##### 路径 C（强烈推荐 · 与 B 一起做）：Contextual Retrieval

参考 Anthropic 官方文章 *"Contextual Retrieval"*（2024-09），把 chunk 切碎后用一个轻量 LLM 调用为每个 chunk 生成"该 chunk 在整篇文档中扮演什么角色"的前缀，然后再 embed。**召回 top-20 错误率降低 49%**。

在我们项目里实现要点：
1. 用 `claude-haiku-4-5` 或 `MiniMax-M2.5-highspeed`（成本低）
2. 整篇文档放 prompt caching（90% 成本降低）
3. 离线一次性处理，写入 `KnowledgeChunk.contextPrefix`
4. embedding 时 embed `contextPrefix + '\n\n' + text`

##### 路径 D（高阶）：Agent-aware Retrieval Query Planner

当一个 case 已经收集了 confirmed facts（如 `userTier=VIP`, `caseType=withdraw_issue`, `region=越南`），KB 检索应该把这些作为 filter 而不是仅当 query 字符串。Agent 调用时自动注入：

```typescript
// kb_hybrid_retrieve 内部
const filters = {
  caseType: caseMemory.caseType,
  locale: caseMemory.confirmedFacts.locale,
  userTier: caseMemory.confirmedFacts.userTier,
}
```

#### 2.4 检索质量评估闭环

任何 RAG 上线都必须有评估，不然就是黑盒。

- **离线评估集**：从 Console / `apps/console/app/admin/...` 导出近 30 天的 case + final resolution，做成 ground-truth 数据集
- **指标**：Recall@5 / nDCG@10 / Citation Precision（Agent 引用的 chunk 是否真的在 ground-truth 里）
- **触发**：每次 ingestion job 完成、reranker 模型升级、prompt 改动 → 自动跑评估
- **看板**：Console → Knowledge Base → "Quality" tab，展示分商户、分 caseType 的召回率趋势

#### 2.5 KB Skill 的提示词要点（写到 Skill description）

```
kb_hybrid_retrieve — 知识检索

调用时机：
- 用户问"怎么做...""为什么..."等说明性问题
- 进入新阶段需要参考标准流程时
- 处理冷僻业务（活动规则、新政策）

不要调用时机：
- 用户报告具体故障（先查后台 API，KB 是补充）
- 用户表达情绪而非提问（先安抚/收集）
- 同一个 query 已调过（避免重复消耗）

返回结果使用方式：
- 把 [KB:xxxx] 引用 tag 放到回答里，方便审计
- 不要逐字 copy snippet，要结合 case context 改写
- 如果 5 条 relevance 都 < 0.4，告诉用户"暂无相关说明，已转人工"
```

### 3.3 Skills 模块的增强建议

当前 `/admin/skills` 编辑器需要手填 JSON Schema、Headers、Mock Fixture，对商务集成不友好。

**建议补的能力**：
1. **OpenAPI / Swagger 导入** — 上传 `swagger.json` 自动生成 skill 列表（商户的 raw_swagger.md 暗示这是个常见场景）
2. **认证模板** — 下拉选择 `apiKey-header` / `bearer` / `basic` / `oauth2-client-credentials`，避免每次手填 headers
3. **环境变量占位符** — Headers 里支持 `${KEY_NAME}`，从环境变量或 KMS 取值
4. **重试 / 熔断配置** — 在 Skill 编辑表里加 `retryCount`, `backoffMs`, `circuitBreakerThreshold`
5. **响应映射 / 字段重命名** — `responseMapping: { "data.status": "accountStatus" }`，避免商户后端字段不规范污染 confirmedFacts
6. **测试台增强** — 现在的"Test"按钮只能跑一次，建议支持 mock vs http 对比、多 query 批量
7. **Skill 版本管理** — 每次修改自增 version，rollout 时可灰度

### 3.4 Routing 模块的现状与缺口

当前 `routings` 表只有 `queue / priority / skillsAllowed / maxWaitingTime / autoAssign` 五个字段，但代码里只读了 `queue`（用作 humanTask 的归属）。

**实际生产应该有的能力（缺失）**：
- **路由规则** — `caseType: deposit_issue, region: VN, severity: high` → `queue: deposit_vip_vn`
- **Operator 池绑定** — `queue → operatorIds[]`，能看每个 operator 的负载
- **班次管理 / 在线状态** — 离线 operator 不分案
- **SLA 配置** — 超过 `maxWaitingTime` 后升级到下一队列
- **多语种路由** — Vietnamese caseType 走 VN queue
- **轮询/最忙最闲/技能匹配三种分案算法**

**建议**：要么补完，要么暂时下线 Routing 模块（只保留 humanTask 的 `queue` 字段作为静态标签），等到真正多 operator 上线时再做。

### 4.2 急需补强的健壮性问题

#### 4.2.1 SubAgent 守护栏不足

`sub-agent.ts` 当前问题：

| 问题 | 现状 | 风险 | 建议 |
|------|------|------|------|
| 超时硬编码 30s | `DEFAULT_TIMEOUT_MS = 30_000` | 长查询（如对账查 30 天）必断 | 改成 per-skill timeout × maxIterations 计算；或暴露到 Console |
| 失败无重试 | abort 直接 throw | 偶发网络抖动直接挂 | 加 1 次 retry（同 prompt + tools），失败再退出 |
| Token 用量未传播 | `totalTokens` 累加但 `LoopResult` 不带 | 主 Agent 无法做"超预算停" | 把 sub-agent token 累加进 caseMemory.subAgentTokenSpent |
| 无 cost cap | 一个 case 可能派 N 个 sub-agent × M 次迭代 | 单 case 烧 $$ | Console 加 `maxCostPerCase` 配置，超额转人工 |
| 子 Agent 工具集无白名单/黑名单 | `buildTools()` 全部加载 | 子 Agent 可能调 finalize_case 等终端工具 | `SubAgentConfig.allowedSkills` 字段，限制工具 |
| Mock 数据回填到真 fact | 子 Agent 用 mock skill 拿到假数据 → merge 到 confirmedFacts | 上线时 mock skill 没替换 → 错误数据进决策 | 在 `mode='mock'` 的 skill 输出加 `__mockWarning__` 标记，merge 时跳过 |

#### 4.2.2 主 Agent Loop 边界场景

| 场景 | 当前行为 | 建议 |
|------|----------|------|
| LLM API 5xx 一直失败 | catch 后 `break` 退出 loop | 加指数退避重试 3 次，failed→ escalated |
| 上下文压缩失败 3 次 | `consecutiveCompactFailures` 计数但没触发动作 | 触发 → emergency snip 到最后 4 条 |
| 同一 tool_use_id 多次出现（provider 兼容 bug） | 重复执行 | 去重 by id |
| 客户在 form 渲染时刷新页面 | form state 丢失 | form 提交前 persist 到 caseMemory，刷新后还能恢复 |
| Case 在 SOP 模式下 todo 全部 cancelled 但未 finalize | 进入"无事可做但 loop 继续"状态 | 检测全 cancelled → 自动 escalate 或 finalize as `cancelled` |
| 同一 user 同时打开两个 chat tab | 两个 tab 都 POST `/api/messages`，并发写同一 case | DB 加乐观锁：`updateMany where updatedAt = lastSeen`，冲突拒绝并提示前端 |
| Case 进入 escalated 后用户继续发言 | 主 loop 不响应（已在新版加了 `stageTools=[]` 简单回复） | 已修；建议再加一个"escalation pending"专用前端气泡，明示用户 |

#### 4.2.3 Streaming Tool Executor 增强

```diff
- timeout: AbortSignal.timeout(definition.timeoutMs || 8000)
+ timeout: AbortSignal.timeout(definition.timeoutMs || 8000),
+ // 重试与熔断
+ retry: { count: definition.retryCount ?? 2, backoffMs: 200 },
+ circuitBreaker: getCircuitBreaker(definition.name)
```

每个 skill 维护熔断器（5 分钟内 50% 失败 → 打开 60s）。

#### 4.2.4 Memory / Compaction 容错

- `compact.ts` 调用 LLM 失败时 fallback 到简单截断（已部分实现）
- `factChangelog` 上限 200，加 ring buffer
- `agentTodos` JSON 字段可能膨胀到几十 KB，建议:
  - 老 case（resolved 7 天前）的 memory 字段做归档（move 到冷存储 / S3）
  - DB 列加 `summary_compressed: Bytes` 用 zstd 压

### 4.3 LLM Provider 抽象与 fallback

目前 `loop.ts` 直接 `new Anthropic(...)`，依赖 baseURL 切 MiniMax / DeepSeek / Anthropic。问题：

- 单个 provider 故障 → 整个 chat 挂
- 不同 case type 想用不同 model 难（虽然 `evaluationModel` 字段有）
- 成本对账困难

**建议**：抽一层 `LlmClient` 接口

```typescript
interface LlmClient {
  stream(req: StreamRequest): AsyncIterable<StreamEvent>
  invoke(req: InvokeRequest): Promise<InvokeResponse>
  getProvider(): 'anthropic' | 'minimax' | 'deepseek' | 'openai'
}

// 实现
class AnthropicCompatibleClient implements LlmClient { ... }
class OpenAIClient implements LlmClient { ... }

// Router
class LlmRouter {
  async stream(req) {
    const primary = this.pickProvider(req.taskType)  // case_chat / policy_eval / stage_eval / fact_extract / kb_rerank
    try {
      return await primary.stream(req)
    } catch (e) {
      if (isProviderDown(e)) return this.fallback(req).stream(req)
      throw e
    }
  }
}
```

并把 `model` 从单 string 改成 task-class → model 映射：

```json
{
  "models": {
    "case_chat":        { "primary": "claude-sonnet-4-7", "fallback": "MiniMax-M2.7" },
    "policy_eval":      { "primary": "MiniMax-M2.7-highspeed", "fallback": "deepseek-v3" },
    "stage_eval":       { "primary": "MiniMax-M2.7-highspeed", "fallback": "deepseek-v3" },
    "fact_extract":     { "primary": "MiniMax-M2.5-highspeed", "fallback": "deepseek-v3" },
    "kb_query_rewrite": { "primary": "MiniMax-M2.5-highspeed", "fallback": "deepseek-v3" }
  }
}
```

### 4.4 数据一致性

- `Case.status` 与 `CaseMemory.caseStatus` 两处都存，容易不同步（已发现 bug）。**单源化**：状态只在 Case 表，CaseMemory 通过 join 取。
- `HumanTask.status` 与 `Case.blocker` 关联但分两处。考虑用一个状态机服务（如 XState）做唯一决策。
- `Skill.enabled` toggle 后旧 in-flight 调用是否生效？现在是请求级缓存，需文档化。

## 五、集成抽象：作为 SDK / API 嵌入第三方 CS 平台

> iGaming 商户的现状：80% 用 **LiveChat**、**Tawk.to**、**Intercom** 或自研 IM 作为客服前端。我们的产品**不是要替换它们**，而是作为"AI 大脑"接入其后端。

### 5.1 目标交付形态

| 形态 | 适用场景 | 接入方式 |
|------|----------|----------|
| **A. Webhook 模式（推荐主推）** | LiveChat / Tawk / Intercom / 自研均支持 | 商户的 IM 平台把消息事件 webhook 给我们；我们 webhook 回复 |
| **B. REST + SSE API** | 商户想完全自己控制 UI | 商户 POST `/v1/messages`，订阅 SSE 拿 token-by-token 输出 |
| **C. Embed iframe** | 商户没有自己的 CS 平台 / PoC | 我们的 `/chat` 页面以 iframe 嵌入 |
| **D. JS SDK** | 商户做轻定制 | `<script src="intera.js"></script>` + `Intera.init(...)` |

### 5.2 公共 API 设计（V1）

#### 5.2.1 认证

- Header: `Authorization: Bearer <api_key>`
- Customer 维度的 API key 在 Console → Settings 生成（当前 schema 已有 `Customer.apiKey` 字段但未启用）
- 加签名校验（HMAC-SHA256 of body + timestamp，防重放）

#### 5.2.2 核心 Endpoints

```
POST /v1/conversations
  → 创建对话（返回 conversationId，等同当前 chatId）
  Body: { externalUserId, locale?, metadata? }
  
POST /v1/conversations/{id}/messages
  → 发送用户消息，SSE 流式返回
  Body: { content, attachments?, externalMessageId? }
  Stream:
    event: text_delta        data: { delta: "您好..." }
    event: tool_executing    data: { name: "get_account_status", displayLabel: "查账号" }
    event: skill_result      data: { name: "get_account_status", result: {...} }
    event: case_update       data: { caseId, status, type, confirmedFacts }
    event: human_handover    data: { reason, queue, ticketId }
    event: message_complete  data: { messageId, tokensUsed, latencyMs }

GET /v1/conversations/{id}
  → 获取对话快照（messages、当前 case、status）

POST /v1/conversations/{id}/operator-handover
  → 通知 Intera 此对话已被人工接管（从 IM 平台触发）
  Body: { operatorId, operatorName }

POST /v1/webhooks  (我们调用商户的)
  事件类型: case.created / case.resolved / case.escalated / human_task.created
  Payload: { event, timestamp, customerId, conversationId, case, signature }
  签名: HMAC-SHA256(body, customer.webhookSecret)
```

#### 5.2.3 Skills 反向调用（商户后端 → 我们）

当 Agent 需要查商户数据（订单、账号、KYC），不再走 Agent 主动 HTTP 调商户 API，而是支持商户**注册一个统一的 webhook receiver**：

```
我们的 SkillRouter 发现 skill.mode === 'webhook'
  → POST 到商户 https://商户域名/intera/skill-callback
  Body: { skillName, input, caseContext, conversationId, callbackUrl, expiresAt }
  
商户收到，处理，POST 回:
  POST /v1/skill-callback/{token}
  Body: { ok: true, output: {...} }
  
我们解锁等待的 Agent loop，继续执行
```

优点：商户内部系统不需要暴露公网，只需主动 outbound 调我们的 callback URL；同时商户可以做权限控制、数据脱敏。

#### 5.2.4 多语言

- Locale 上下文化：`POST /v1/conversations` 时携带 `locale=vi-VN`，Agent 系统 prompt 自动追加 "Reply in Vietnamese" 段
- KB 检索 filter `locale=vi-VN` 优先（前面已提）
- 错误消息 / SSE event 内的 `displayLabel` 走 i18n 字典（Console 配置）

### 5.3 LiveChat 深度集成方案

> 本节基于 LiveChat Agent Chat API v3.5，提供可直接落地的技术设计，并附自有 LiveChat 账号沙盒验证步骤。

#### 5.3.1 Bot Agent 架构概述

LiveChat 原生支持 Bot Agent 接入，整体数据流如下：

```
顾客发起对话
    │
    ▼
LiveChat 平台（路由到分配了 Bot 的 Group）
    │  Webhook: incoming_chat
    ▼
Intera Adapter  →  /v1/livechat/webhook
    │  建立 chat_id → caseId 映射
    │  调 POST /v1/conversations/{id}/messages（内部）
    ▼
Intera Core Agent（现有 AgentLoop）
    │  SSE 流式输出
    ▼
Adapter 收集输出
    ├─ text_delta 第一个 chunk → 发 typing_on indicator
    ├─ 收集完整回复 → send_event（LiveChat Agent Chat API）
    ├─ ask_user_question Skill → Rich Message Quick Replies
    ├─ kb_hybrid_retrieve 结果 → Rich Message Cards
    └─ 需要人工（create_human_task）→ transfer_chat → 真人 Group
```

LiveChat 有两种 Bot 接入方式：

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| **Bot Agent（推荐）** | 注册为虚拟客服，LiveChat 自动把对话路由给它 | AI 完全接管首轮，需要时转真人 |
| **Webhook 监听** | 不占 Agent 席位，监听所有事件 | AI 作为辅助建议，真人仍然主导 |

iGaming 场景推荐 **Bot Agent 模式 + 人工兜底**。

#### 5.3.2 LiveChat 开放 API 能力全表

| API 类别 | 关键动作 | 参数 / 说明 |
|----------|---------|------------|
| **Agent Chat API** | `send_event` | 向对话发送文本 / Rich Message |
| | `transfer_chat` | 将对话转移给真人 Agent 或 Group |
| | `update_chat_properties` | 写入自定义属性（存 `intera_case_id`、`case_type` 等）|
| | `tag_chat` | 打标签（`ai_resolved` / `escalated` / `case_type:deposit`）|
| | `send_typing_indicator` | 发送/停止打字状态指示 |
| | `deactivate_chat` | 关闭/归档对话 |
| **Webhooks（入站）** | `incoming_chat` | 新对话触发（Bot 接管的入口）|
| | `incoming_event` | 顾客发新消息 |
| | `chat_transferred` | 对话被转移（Bot→人工 或 人工→Bot）|
| | `chat_deactivated` | 对话结束 |
| | `user_added_to_chat` | 真人客服加入对话 |
| **Configuration API** | Bot 管理 | 创建/查询 Bot Agent，绑定 Group |
| **Rich Messages** | `quick_replies` | 快速选项按钮（`ask_user_question` 的 LiveChat 形态）|
| | `cards` | 富媒体卡片（KB 文章展示）|
| | `carousel` | 多张卡片轮播 |

> **人工交互支持结论**：✅ LiveChat 的 `transfer_chat` API 完整支持 Bot → 真人无缝接管。真人操作完全在 LiveChat 原生界面中进行，**客服零学习成本**。

#### 5.3.3 Human Handover 完整流程

```
① Intera Agent 决策需要人工（调用 create_human_task）
    │
    ▼
② Adapter 调用 LiveChat transfer_chat：
   POST https://api.livechat.com/v3.5/agent/action/transfer_chat
   Authorization: Bearer <bot_token>
   {
     "chat_id": "PJ0MRSHTDG",
     "target": {
       "type": "group",
       "ids": [2]           // Console 配置的 escalation_livechat_group_id
     }
   }
    │
    ▼
③ LiveChat 通知真人客服（原生界面铃声 + 消息提醒）
   同时 Adapter 发一条文本给顾客：
   "正在为您连接人工客服，请稍候..."
    │
    ▼
④ Intera 监听 webhook：user_added_to_chat
   确认真人进入 → 更新 DB：Case.status = 'waiting_human'
   Bot 进入静默模式（收到 incoming_event 只记录，不触发 AgentLoop）
    │
    ▼
⑤ 真人处理完毕：
   方案 A：真人关闭对话 → chat_deactivated webhook
           Adapter 更新 HumanTask.status = 'resolved'
           触发 ConsultationAgent finalize_consultation 流程

   方案 B：真人主动转回 Bot（transfer_chat target=bot）
           chat_transferred webhook → Bot 重新接管
           继续 AgentLoop（注入 "[System] 人工处理完毕，结论: ..."）
```

**实现要点**：
- `transfer_chat.target.ids` 对应 Console → Routing → 新增字段 `livechatGroupId`（各 case type / 队列对应不同 Group）
- 人工处理期间 Bot token 仍在，可接收事件更新 CaseMemory
- `update_chat_properties` 写入 `intera_case_id`，让真人在 LiveChat 界面看到案件编号，可一键跳转 Console 详情页

```typescript
// packages/adapters/livechat/rich-message.ts

export function skillOutputToRichMessage(
  skillName: string,
  output: unknown,
): LiveChatRichMessage | null {

  // ask_user_question → quick_replies
  if (skillName === 'ask_user_question') {
    const q = output as { question: string; options: string[] }
    return {
      template_id: 'quick_replies',
      elements: [{
        title: q.question,
        buttons: q.options.map(opt => ({
          type: 'message' as const,
          text: opt,
          value: opt,
        })),
      }],
    }
  }

  // kb_hybrid_retrieve → cards（前 3 条 relevance > 0.5）
  if (skillName === 'kb_hybrid_retrieve') {
    const r = output as { results: Array<{ title: string; snippet: string; url?: string; relevance: number }> }
    const cards = r.results
      .filter(x => x.relevance > 0.5)
      .slice(0, 3)
      .map(x => ({
        title: x.title,
        subtitle: x.snippet.slice(0, 100) + '...',
        buttons: x.url
          ? [{ type: 'url' as const, text: '查看详情', value: x.url }]
          : [],
      }))
    if (cards.length === 0) return null
    return { template_id: 'cards', elements: cards }
  }

  return null   // 其他 skill 走纯文本
}
```

##### 平台限制说明

| Rich Message 类型 | LiveChat 支持 | 对应 Intera Skill |
|-------------------|--------------|-------------------|
| Quick Replies（按钮选项）| ✅ 完整支持 | `ask_user_question` |
| Cards（文章卡片）| ✅ 完整支持 | `kb_hybrid_retrieve` |
| Carousel（多卡片）| ✅ 支持 | 多文章结果 |
| 表单输入 Form Fields | ❌ 不支持 | 表单类交互仍用纯文本提示 |
| 文件上传提示 | ⚠️ 仅限 LiveChat 自有上传控件 | 需要 KYC 等文件时给文字提示 |

> 表单类场景（如让顾客输入订单号）在 LiveChat 里只能用文字提示，这是平台限制，与 Intera 无关。Intercom 的 Custom Bot 支持 Input Block，如需表单体验可优先考虑 Intercom。

#### 5.3.5 会话状态映射与并发安全

新增 DB 表（`packages/shared/prisma/schema.prisma`）：

```prisma
model ExternalConversation {
  id             String    @id @default(cuid())
  platform       String    // 'livechat' | 'intercom' | 'tawk'
  externalChatId String    // LiveChat chat_id
  internalCaseId String?   // 关联的 Intera caseId
  customerId     String
  status         String    @default("active") // active|transferred|closed
  transferredAt  DateTime?
  closedAt       DateTime?
  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt

  @@unique([platform, externalChatId])
  @@index([customerId, platform, status])
}
```

**并发安全**：LiveChat webhook 可能并发投递（顾客快速连发 3 条消息，LiveChat 并发触发 3 次 `incoming_event`）。

处理策略：
1. 每个 `chat_id` 进入 webhook 时在 Redis 加锁（key: `lc_lock:{chat_id}`，TTL 10s）
2. 锁等待超时（1s）→ 直接回 HTTP 200 给 LiveChat（防重投机制），消息推入 BullMQ 队列
3. 队列 worker 按 `chat_id` 分 partition 串行处理，保证顺序

#### 5.3.9 Intercom 集成（简述）

#### 5.3.10 Tawk.to / 自研 IM

## 六、多租户、数据隔离、配额与限流

### 6.1 多租户

**当前问题**：所有路由硬编码 `customerId='default'`（如 `messages/route.ts:711` 默认值、`config-changed` 默认 default）。

**改造步骤**：
1. **API 请求必带 customerId**：从 API key 反查（`apiKey → customerId` 索引），不允许 URL 参数传入
2. **所有 DB 查询带 customerId**：Prisma extension 中间件强制 where 子句注入
3. **跨租户隔离测试**：写集成测试覆盖"A 商户的 API key 不能拿到 B 商户的 case"
4. **Console 区分平台管理员 vs 商户管理员**：超管能切租户，商户只能看自己

### 6.2 配额与限流

| 资源 | 限流维度 | 建议默认 |
|------|----------|----------|
| `/v1/messages` QPS | per customer | 50/s burst, 20/s sustained |
| Case 同时进行数 | per customer | 1000，可购买扩容 |
| Tokens 日消耗 | per customer | 软上限 10M，超出邮件告警 |
| 单 case Token | per case | 100K，触发 emergency snip |
| KB 检索 QPS | per customer | 100/s |
| Sub-agent 并发 | per case | 3（已有 `maxParallelAgents`） |
| HumanTask 队列长度 | per customer/queue | 500，超出报警 |
| Skill webhook 重试 | per skill call | 3 次 |

实现：用 Redis + `rate-limiter-flexible` 库，或者数据库的滑动窗口表。

### 6.3 数据隔离

- 不同 customer 的 Case / CaseMemory / Message 物理同库，逻辑隔离（schema 都已有 customerId）
- 大客户（>10% 流量）支持迁移到独立 schema 或独立 DB
- KB 向量索引：`KnowledgeChunk` 表加 `customerId` 列 + 复合索引 `(customerId, embedding)`，pgvector 的 HNSW 索引支持 partial 索引按 customerId 切

### 6.4 加密

- DB 整库：Postgres TDE 或云厂商托管加密
- 敏感字段（手机号、卡号、KYC 文件 URL）：列级加密（pgcrypto / app 层 AES-GCM）
- API key / Skill HTTP headers 的密钥：KMS 托管，DB 只存 reference

## 八、合规、PII 与安全

### 8.1 iGaming 行业特殊要求

| 维度 | 要求 | 当前 | 建议 |
|------|------|------|------|
| 数据驻留 | 部分牌照（如 IoM、马耳他）要求数据在地境内 | 单部署 | 支持多 region 部署，customer 注册时选 region |
| 反洗钱 / 反诈 | 大额提现、可疑模式需上报 | 无 | Agent 拿到 transaction 数据时 hook 到 AML 引擎 |
| 自我排除 / 责任博彩 | 用户标记 "self-excluded" 不能被怂恿玩游戏 | 无 | Skill 返回 `userFlags: ['self_excluded']` 时 Agent prompt 自动注入禁止条款 |
| KYC | 验证状态必须能查 | ✅ `get_kyc_status` skill 占位有 | 上线接真接口 |
| 操作审计 | 监管要求 1-5 年保留 | Message 已存 DB | 加 immutable trail（append-only audit log，hash chain） |

### 8.2 PII 处理

- **入站脱敏**：用户上传卡号 / 身份证号 / 手机号 → 在写 `Message.content` 前 mask（保留后 4 位）
- **LLM 前过滤**：发送给 LLM 的消息也走脱敏（避免训练泄漏）
- **日志脱敏**：`debug-logs/` / Sentry / Datadog logs 自动脱敏
- **GDPR 用户请求**：
  - 数据导出 — 已有 `/api/cases/[id]/export`，扩展到全量 user 数据
  - 删除请求 — 新增 admin 操作，按 `externalUserId` 软删 / 硬删 + Sub-agent / KB 引用清理

### 8.3 应用层安全

- **CSRF**：API 请求要求 `Origin` / `Referer` 校验或 token
- **Prompt Injection 防护**：
  - System prompt 与 user content 用 XML tag 包裹（部分已做 `[INTERA MODE: ...]`）
  - 出现明显注入模式（"ignore previous instructions"）→ Policy 拦截
  - Skill 输出回灌前过滤（已有 `StreamingTextSanitizer`）
- **SSRF**：Skill `endpoint` 必须是 whitelist 域名或商户已注册域名
- **Webhook 签名校验**：所有入站 webhook 必须验签
- **依赖审计**：CI 跑 `npm audit` + Snyk

## 十、灰度、A/B 与回滚

### 10.1 配置变更灰度

当前 `/admin/agent` 改完立即生效（`config-changed` 路由推 cache invalidation）。生产风险：一个 prompt 改坏所有客户立即受影响。

**建议机制**：
- 每个配置项有 `draft / staged / published` 三态
- `staged` 可指定灰度规则：`5% traffic` / `specific userId list` / `specific case type`
- 看 metrics 7 天后一键 promote 到 `published`
- 一键 rollback 到上一版本

DB schema 增量：
```prisma
model ConfigVersion {
  id           String   @id @default(cuid())
  customerId   String
  resourceType String   // "agent_prompt" | "case_type" | "skill" | "policy"
  resourceId   String
  version      Int
  payload      String   @db.Text
  status       String   // draft|staged|published|archived
  rolloutRule  String?  // JSON: { percent: 5, userIds: [...] }
  publishedAt  DateTime?
  publishedBy  String?
  rolledBackAt DateTime?
  @@index([customerId, resourceType, resourceId, version])
}
```

### 10.2 模型 A/B

- 把当前 model 升级到 `models: { ... }` 的 task-class 配置（前面 4.3 提过）
- 每条 message 随机分桶 `bucket = hash(conversationId + experimentId) % 100`
- bucket < 10 → variant_B，否则 → variant_A
- 看板对比 variant_A vs variant_B 的：解决率、token 成本、用户满意度（前端加 thumbs up/down）、人工接管率

### 10.3 Skill 灰度

修改 Skill endpoint 时（如从老 API 切新 API），灰度 5% 流量 7 天 → 100%。

## 附录 A：核心数据流 cheat sheet

```
顾客发消息
  → POST /api/messages
  → AgentLoop.run(userMessage)
    → ingestUserMessageFacts(LLM 抽事实)
    → while (iter < max):
        → 构造 prompt + tools
        → anthropic.messages.stream()  ← 这里要支持 prompt cache
        → 边流边执行 tools (StreamingToolExecutor)
          → mode='mock'  → 返回 fixture
          → mode='http'  → fetch(endpoint) + 重试 + 熔断
          → mode='webhook' → 推商户 callback（新）
        → preTool / postTool / preFinalize policies
        → 终端 tool:
          - create_case   → 落库
          - finalize_case → status=resolved
          - create_human_task → status=waiting_human
          - finalize_consultation → operator 闭环
    → 持久化 messages / memory / traces

operator 上线 chat
  → POST /api/human-chat
  → ConsultationAgent.run(operatorMessage)  ← 独立 class, 仅 finalize_consultation
    → loop: stream → optional tool → DB write

后台 worker
  → 轮询 needsContinuation=true 的 case
  → 调 /api/messages 注入 system message 恢复执行
```
