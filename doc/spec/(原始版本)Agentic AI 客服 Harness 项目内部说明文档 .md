# 1. 这份文档是要解决什么问题

在开始做产品之前，我们需要先统一一个非常核心的认知：

> 我们要做的不是一个“更高级的客服机器人”，也不是一个“基于低代码流程编排的智能客服”。

我们想做的是：

> **一套由 Agent 主导、以问题解决为目标的 AI 客服 Harness SaaS。**

如果这个认知没有统一，团队很容易默认把项目理解成以下几类传统产品：

- FAQ 机器人
- 问答增强版客服机器人
- 基于知识库的 RAG 客服
- 带工作流节点的低代码客服平台
- “收集信息 → 调接口 → 转人工”的自动化客服系统
  - 

这些都不是我们真正想做的东西。

# 2. 一句话解释我们想做什么

**用户只要提出需求，Agent 就持续接管问题，主动提问、主动调查、主动调用工具、主动找人工确认，直到真正解决问题。**

## 更准确的版本

我们要做的是一个 **Agentic Customer Service Harness**：

- 用户面对的永远是 Agent
- Agent 负责理解目标、规划步骤、收集证据、调用工具、协调人工、持续推进
- 人工不是“接管对话的人”，而是 Agent 背后的一个资源节点
- 系统的目标不是“回复一轮消息”，而是“把 Case 处理到闭环”
  - 处理单元不再是 "message"  而是 **"case"**
  - 

# 3. 为什么传统 AI 客服不够

当前大多数 AI 客服，哪怕加了工作流、知识库、模型路由，本质上还是下面这套逻辑：

## 传统逻辑

1. 用户发一句话  
2. 系统识别意图  
3. 命中 FAQ 就回答  
4. 需要查询就收集字段  
5. 字段收集完调一次接口  
6. 不会处理就转人工  
   1. 

这种方式的问题在于：

### 1）它是“消息响应式”的，不是“问题解决式”的

系统只会对当前这条消息做反应，不会真正持有问题。

### 2）它没有真正的 case ownership

没有一个执行主体负责“把事情做完”。

### 3）它无法持续推进复杂问题

一旦问题需要：

- 多次查询
- 多来源核对
- 人工确认
- 状态等待
- 中途恢复
  - 

传统客服机器人就会迅速退化成“请稍等，我帮您转人工”。

### 4）人工和 AI 是割裂的

一旦转人工，通常意味着：

- 用户重新描述问题
- 人工重新理解上下文
- 机器人前面的工作价值被打断
  - 

### 5）低代码平台只是把旧逻辑做得更可配置

低代码流程平台的提升点是“搭建更方便”，但底层范式通常没变。  

它依然是：

- 节点流
- 分支判断
- 固定槽位收集
- 固定 API 调用
- 不会处理就转人工

# 4. 我们和传统低代码 AI 客服平台的根本区别

## 4.1 本质区别：我们不是在做“Flow-Chatbot”

### 传统低代码客服平台

核心是：

> 预先设计好的流程图 + 规则树 + 节点跳转

特点：

- 先定义场景
- 再定义每一步问什么
- 用户尽量按流程走
- 流程外情况很难兜住
- 本质是“自动化流程执行器”
  - 

### 我们要做的 Agentic Harness

核心是：

> 一个围绕 Case 运行的 Agent 执行系统

特点：

- 不要求预先写完所有流程
- Agent 根据当前目标和证据动态决定下一步
- 可以中途改计划
- 可以串联多个动作
- 可以请求人工
- 可以恢复执行
- 本质是“任务闭环执行器”
  - 

## 4.2 传统产品和我们要做的产品的对比

| 维度     | 传统低代码 AI 客服 | 我们要做的 Agentic Harness |
| -------- | ------------------ | -------------------------- |
| 核心单位 | Message / Intent   | Case / Goal                |
| 系统目标 | 回答问题           | 解决问题                   |
| 交互模式 | 一问一答           | Agent 主导推进             |
| 信息处理 | 槽位收集           | 证据收集                   |
| 执行能力 | 固定流程节点       | 动态计划 + Tool 调用       |
| 知识能力 | FAQ / RAG 回答     | 检索作为证据供 Agent 决策  |
| 人工模式 | 转人工接管会话     | 人工作为 Agent 背后的工具  |
| 状态管理 | 会话上下文         | 持久化 Case 状态           |
| 异常处理 | 流程外转人工       | 重规划 / 补证据 / 调人工   |
| 复杂问题 | 容易断裂           | 可持续推进                 |
| 产品形态 | 智能机器人         | 客服 Agent 操作系统        |

# 5. 我们产品的核心理念

## 5.1 Agent 是 case owner，不是聊天窗口

Agent 不只是负责说话，它要负责：

- 理解目标
- 提出澄清问题
- 制定处理计划
- 组织证据
- 调技能
- 调人工
- 给阶段性反馈
- 最终形成结论
  - 

换句话说：

> Agent 要对“问题有没有被推进、有没有被解决”负责。

## 5.2 检索不是为了“直接回答”，而是为了“支持行动决策”

传统 RAG 客服的逻辑是：

- 用户提问
- 检索知识库
- 拼出回答
  - 

但我们的系统里，检索只是 Agent 的一个输入源。

例如，Agent 检索知识后可能决定：

- 直接解释给用户
- 继续问一个关键问题
- 去查供应商 API
- 判断这是个高风险 case
- 请求人工确认某条政策例外
  - 

所以检索层的价值不是“生成一段像样的话”，而是：

> **给 Agent 提供可引用、可验证、可行动的证据。**

## 5.3 人工不是转接对象，而是后台资源

传统 AI 客服碰到问题不会处理时，会说：

- “我帮您转人工”
- “请联系客服专员”
- “请稍后等待人工协助”
  - 

这意味着前台体验断掉了。

我们要做的是：

> Agent 自己去找人工。

也就是说：

- Agent 把问题总结好
- Agent 把证据准备好
- Agent 把需要确认的点结构化提出来
- 人工只需要回答那个问题
- Agent 再把结果带回给用户
  - 

用户看到的仍然是同一个 Agent。

这件事一旦做好，体验会非常强，因为用户感受到的是：

> “这个客服会持续帮我跟进，哪怕内部需要找人确认，也不用我再去和别人重新沟通。”

## 5.4 我们不是在做“收集信息”，而是在做“收集证据”

传统客服机器人通常围绕字段设计，比如：

- user_id
- amount
- txn_id
- screenshot
  - 

这没错，但太窄了。

因为真实世界里，解决问题需要的并不只是字段，还包括：

- 文档知识
- 历史 case
- 图片内容
- API 查询结果
- 风控判断
- 人工意见
- 系统日志
- 配置规则
- 厂商状态
  - 

所以我们应该从“字段收集”升级为：

> **Evidence Collection（证据收集）**

这能让系统更适配复杂场景，而不是被槽位填充模型限制住。

# 6. 产品核心结构是什么

可以把整个系统理解成 5 个核心部分。

## 6.1 Agent Orchestrator

这是大脑。负责：

- 理解目标
- 生成计划
- 决定下一步动作
- 读取结果后继续推进
- 持有整个 case 状态
  - 

它运行的不是“固定流程图”，而是一个 ReAct 风格的循环：

- Understand
- Clarify
- Plan
- Act
- Observe
- Continue / Resolve
  - 

可以参考 https://arxiv.org/abs/2210.03629

## 6.2 Retrieval Layer

这是知识与事实的召回层。

我们计划采用的方向是（仍在探索更优的路径，例如wiki llm处理QA量小的场景）：

- BM25
- 向量切片 RAG
- grep / code search / config search
  - 

这点很重要，因为在很多企业真实客服里，答案不一定只在 FAQ，而可能在：

- markdown runbook
- changelog
- 配置文件
- SOP
- 内部接入文档

所以我们做的不是“一个知识库问答器”，而是：

> 多源事实检索系统。且支持在 harness 后台自行混合调配。

## 6.3 Skill Runtime

这是系统的执行层，Agent 可以调用各种 skill。

比如：

- 查订单
- 查游戏厂商 API
- 查支付渠道
- 查账号状态
- 查风控
- 发起补单
- 提交异常工单
- 请求活动资格核验
  - 

Skill 的作用是让 Agent 真正能“做事”，而不是只会说话。

## 6.4 Human-as-a-Tool

这是人工协作层。

使用原则：

- 人工不是默认接管会话的人
- 人工是 Agent 能调度的一个异步节点
- 人工处理的是结构化问题
- Agent 处理的是用户沟通
  - 

这个设计会直接影响产品体验和平台效率。

## 6.5 Case Memory

这是系统持续性的关键。

> 目前我们计划在 Claude Code 四层上下文压缩的 context engineering 上做客服场景的适配，并加一些额外的创新点。
>
> 例如在 harness 层面把 key events inject into prompt cache 并在case处理完后取出，以达到 成本和性能的 trade off

系统必须记住的不是聊天记录本身，而是 case 的处理状态，比如：

- 当前目标
- 已确认事实
- 未确认事实
- 已调用过哪些 skill
- 收到了哪些结果
- 人工是否已经回复
- 当前阻塞在哪里
- 是否已经进入高风险模式
  - 

没有这个，系统就会退化成“每一轮都像重新开始”。

# 7. 一个例子：传统客服怎么做，我们想怎么做

## 场景：用户说“我昨天充值了还没到账”

### 传统低代码客服的做法

1. 识别意图：充值未到账  
2. 开始收集字段  
   1. 用户名
   2. 金额
   3. 时间
   4. 渠道
   5. 订单号
   6. 截图
3. 字段收集完调一次接口  
4. 如果接口能判断就回复  
5. 如果不确定就转人工  
   1. 

这里的核心问题是：

- 流程很固定
- 用户必须配合字段结构
- 中途异常不好处理
- 人工接手后仍然可能重新核实
  - 

### 我们想要的做法

1. Agent 判断目标：充值异常，先建立 case  
2. Agent 判断下一步需要的最小证据是什么  
   1. 先问最关键的缺失项 ，而不是一口气全问完  
3. Agent 检索知识  
   1. 看是否有渠道延迟公告 （在我们对接的客户中就碰到游戏临时的通告没有被及时地放进API，此类情况可让客户自行在 harness 后台配置 全局的通告，agent 会自行读取，从而减轻我们的工作量）或已知问题  
4. Agent 调 skill  
   1. 查平台订单
   2. 查支付供应商状态
   3. 核对金额和时间窗
5. 若平台和供应商结果冲突  
   1. Agent 发起人工确认任务  
   2. 人工只回答“该笔是否需要补单/是否命中异常队列”  
6. Agent 拿到人工结论后继续回复用户  
   1. 告知当前判断
   2. 是否已提交处理
   3. 还需不需要补截图或等待
      - 

这个过程中，用户始终面对的是同一个 Agent。  

而 Agent 其实在后台完成了：

- 检索
- 询问
- 查询
- 对账
- 找人工
- 恢复执行
- 输出结论
  - 

这就是差异。

# 8. 为什么说这比“低代码工作流”更难，但也更有价值

## 8.1 更难的地方

因为我们不是在做一个静态流程系统，而是在做一个**动态任务执行系统**。

难点包括：

- 如何让 Agent 稳定决策下一步
- 如何管理 case 状态
- 如何让工具结果可被消费
- 如何设计人工回流机制
- 如何做风险控制
- 如何防止模型乱做决定
- 如何平衡自主性和可控性
  - 

## 8.2 更有价值的地方

因为一旦做成，价值不是“回答更像人”，而是：

- 真正减少用户来回沟通成本
- 让 AI 承担问题推进责任
- 把人工从前台接待变成后台专家资源
- 让复杂问题也能有连续性处理能力
- 形成更高壁垒的平台能力
  - 

换句话说：

> 低代码客服平台优化的是搭建效率；  
>
> 我们要优化的是问题处理效率和端到端闭环能力。

# 9. 我们产品的边界：我们要做什么，不做什么

## 9.1 我们要做的

### 1）做一个 Agent-first 的客服平台

不是 chatbot first，而是 case execution first。

### 2）做一个以“解决问题”为中心的系统

而不是以“生成回复”为中心。

### 3）做一个能统一调度知识、工具、人工的执行层

不是把这些能力散落在不同产品里。

### 4）做一个可配置 SaaS 底座

可以适配多个行业，而不是写死在单一业务流程里。

## 9.2 我们现阶段不做的

### 1) 不做单纯 FAQ Bot

### 2) 不做仅服务某一个垂直场景的硬编码流程引擎

### 3) 不以“降低转人工率”作为主要目标

### 4) 不以端到端完全无人工参与作为必须前提

# 10. 团队在设计时需要改变的思维方式

这部分也很重要，因为不同职能容易惯性沿用旧思路。

## 10.1 产品设计上

不要再先问：

- 这个场景应该有哪些意图？
- 要收集哪些字段？
- 流程图怎么画？
  - 

而是先问：

- 用户真正的 goal 是什么？
- 这个 goal 的闭环标准是什么？
- 为了推进到下一步需要什么证据？
- 哪些动作可以自动做？
- 哪些动作需要工具？
- 哪些动作需要人工确认？
- Agent 如何知道何时继续、何时暂停、何时结束？
  - 

## 10.2 研发实现上

不要只把系统理解成：

- LLM + workflow + API
  - 

而要理解成：

- Case state store
- Action runtime
- Retrieval fabric
- Tool protocol
- Human task system
- Guardrail policy
- Agent loop
  - 

## 10.3 算法设计上

不要只优化：

- 意图分类
- FAQ 召回
- 回复文案
  - 

还要重点考虑：

- 计划生成
- 动作选择
- 证据整合
- 工具调用判断
- 冲突处理
- 恢复执行
- 风险约束
  - 

## 10.4 运营与实施上

不要只想着：

- 配多少 FAQ
- 配多少话术
- 配多少流程节点
  - 

而要考虑：

- 哪些数据源能接入
- 哪些工具最值得做成 skill
- 哪些人工问题可以标准化
- 哪些 case 最适合先闭环自动化
- 哪些策略必须强约束
  - 

# 11. 我们的差异化壁垒会来自哪里

如果未来要回答“凭什么是我们”，我们认为壁垒主要不在“模型更强”，而在下面这些系统能力：

## 12.1 Case-centric orchestration

大部分产品停留在会话层，我们如果能把 case 持有和持续推进做好，会形成明显优势。

例如我刷到的小红书一个AI 客服供应商：

> 普通AI客服只能回答，真AI客服才能降本！ 还在把“会... http://xhslink.com/o/4Cs04ZIJX7l 
>
> 复制后直接打开【小红书】，笔记就在那里等你。

此类单纯的一问一答式客服，甚至包括老牌的 live chat、intercome 等AI 客服产品 在2026年仍然具有一定的 market share， 但我们要做的是具有一定颠覆性的，能够尽早占领 AI 客服市场的 绝对优势产品。

因为，理论上，除了模型供应商（Google, Anthropic, XAI, OpenAI 等）的工作极具内卷与技术壁垒，在有了AI coding 提效的加持，Harness / SaaS 产品的成功， 个人认为是取决于如何把最先进的技术玩出名堂来，产品的：

1. 创新点
2. 抢占市场的时机点
3. 能否把握目标客户的痛点

才是最重要的。

而目前在市场越来越大（不仅限于游戏，还有电商、任何产品的售后客服等）AI 客服领域，急需一个能真正能处理 case by case 的Agent！

## 11.2 Human-as-a-tool

这将是非常强的差异化点。  

市场上很多产品仍然把人工当作兜底接管，而不是 Agent 的可调度资源。

来源于 Kilo 的灵感，我们完全可以把 人工客服 抽象成Agent可以调用的工具， 与此同时，我们仍然可以保留一定的灵活性，在 SaaS 后台 可配置是否为一些保守企业设置人工完全接管。

## 11.3 多源检索融合

不是简单切片+向量库，而是可混合配置：

- BM25
- Vector DB
- grep / config / code search
- 动态上下文拼装 （Wiki）
- ... 等前沿技术
  - 

这个对企业真实复杂环境非常关键。

## 11.4 Skill-first execution

一旦 skill 体系搭起来，Agent 就不再只是“会说”，而是“能做”。

## 11.5 可审计、可恢复、可配置的 SaaS 底座

真正能商用的平台，必须不是 demo agent，而是：

- 可控
- 可配置
- 可观测
- 可恢复
- 可审计
  - 

# 12. 第一阶段我们真正要验证什么

MVP 不需要一开始就证明“万能 Agent 客服”成立。  

第一阶段更现实的验证目标应该是：

## 12.1 验证 Agent 是否能持有一个 case

用户提一个问题后，系统能不能一直围绕这个 case 推进，而不是掉回一问一答。

## 12.2 验证 Agent 是否能主动推进

Agent 能不能：

- 问对问题
- 不乱问
- 选对 skill
- 根据结果继续下一步
  - 

## 12.3 验证人工后台协作模式是否成立

也就是：

- Agent 发给人工的任务是否足够清晰
- Agent 是否能消费人工结果并继续服务用户
- 在人工介入的中途，确保顾客可以继续提问其他case，探索多 case 并行处理
  - 

## 12.4 验证混合检索是否真的比传统 向量检索 更有用

我们不是为了堆技术，而是要确认：

- 多源召回能不能真正支撑决策
- grep / config search 是否在真实场景里有明显增益
  - 

## 12.5 验证用户是否感知到“持续解决问题”的体验差异

这点非常关键。  

用户是否会明显感觉到：

- 不用反复解释
- 不用自己切换对象
- 问题在被持续跟进
- 结果比传统机器人更靠谱

# 13. 为什么我们不仅要重做前台，也要重构后台

### 传统低代码平台后台的核心问题是：

“这条流程怎么搭？”

### 我们后台的核心问题是：

“这个 Agent 在这个业务域里应该如何理解问题、如何行动、如何调用资源、如何与用户交互、如何被约束、如何被观测和优化？”

# 14. 交付/实施/运维角色会发生什么变化

## 14.1 传统低代码客服平台中的人员职责

传统平台里，交付和运维主要围绕“流程搭建”展开：

### 典型工作内容

- 拆解客户场景
- 设计意图树
- 配置节点流转
- 设置字段收集顺序
- 配置 FAQ 话术
- 连接几个 API
- 配人工转接
- 调整异常分支
- 做简单知识维护和线上巡检
  - 

### 其本质是

> **把客户需求翻译成流程图。**

这种模式的上限，取决于：

- 流程是否覆盖全
- 节点是否配得细
- 分支是否足够多
  - 

## 14.2 在 Agent Harness 里的新职责

在我们的系统里，交付/实施/运维的角色会升级，不再主要是“画流程图的人”，而更像：

- Agent 解决方案设计师
- Skill 集成工程师
- 知识与检索策略工程师
- UX 对话交互设计师
- Policy / Risk 配置人员
- Agent 运营与评估人员
  - 

### 典型工作内容会转向：

#### 1）定义业务域和 case 类型

- 哪些问题属于同一类 case
- 每类 case 的目标是什么
- 什么叫“解决”
- 哪些情况属于阻塞
- 哪些情况需要人工确认
  - 

#### 2）建设 Agent 可调用的 skills

- 接第三方 API
- 接内部系统
- 接 CRM / ticket / payment / game vendor
- 把原来 scattered 的接口封装成标准 skill
  - 

#### 3）配置 Agent loop 的关键检查点

不是写死“第一步问 A、第二步问 B”，而是配置：

- 什么时候需要先澄清
- 什么时候先检索知识
- 什么时候优先调 skill
- 什么时候必须做人审
- 什么条件下中止自动推进
- 什么条件下可以直接闭环
  - 

#### 4）配置混合检索策略

- 哪类问题优先 BM25
- 哪类问题优先向量召回
- 哪类问题要 grep / config search
- 如何做 rerank
- 哪些知识源更可信
- 不同顾客如何隔离知识与策略
  - 

### 5）配置记忆体

- 采用什么记忆模块
- 如何配置 cron jobs 去收集记忆/存档
- 什么时候让Agent读取哪个记忆
- 哪些记忆需要被提取并被 inject 到 prompt cache
  - 

#### 5）设计 UX 交互方式

- 哪些场景用文本追问
- 哪些场景用表单
- 哪些场景用文件上传
- 哪些场景显示进度状态
- 哪些场景需要确认卡片
- 哪些场景需要给用户阶段性汇报
  - 

#### 6）配置 Human-as-a-Tool

- 哪类问题发给哪个人工队列
- Agent 应如何总结问题
- 人工返回结果用什么结构
- 超时后如何 fallback
- 人工回流后 Agent 如何恢复
  - 

#### 7）持续观察和优化 Agent 行为

- 哪些 case 卡住
- 哪些 skills 成功率低
- 哪些检索源噪声大
- 哪些 loop checkpoint 设计不合理
- 哪些交互会导致用户流失或误解
  - 

### 本质上变成

> **把客户需求翻译成 Agent 的能力系统，而不是翻译成流程图。**

# 15. 我们后台的核心设计理念

我们的后台不应该叫“流程设计器”，而应该是类似：

- Agent Console
- Harness Studio
- Case Agent Admin
- Support Agent Builder
  - 

它的目标不是让我们交付人员“拼流程”，而是完成以下几类配置：

1. ## 配 Agent 的认知环境

Agent 能看到什么、理解什么、记住什么。

1. ## 配 Agent 的行动能力

Agent 可以调用哪些工具、哪些人工、哪些动作。

1. ## 配 Agent 的决策边界

什么时候能自动做、什么时候只能建议、什么时候必须审批。

1. ##  配 Agent 的交互方式

如何向用户提问、展示进度、请求凭证、返回结果。

1. ## 配 Agent 的运营闭环

如何观测、评估、调优、回放和发布。

# 16. 后台应该有哪些核心配置模块

## 16.1 业务域 / Case Schema 配置

### 目标

定义这个顾客的业务世界长什么样，让 Agent 知道“在什么语境里工作”。

### 需要配置的内容

- Case 类型
- 业务类别
- 目标定义
- case 状态机
- 关键实体
- 证据类型
- 解决标准
- 阻塞标准
- 升级条件
  - 

### 示例

比如某个顾客配置：

- `deposit_issue`
- `withdrawal_issue`
- `account_access`
- `promo_eligibility`
- `vendor_game_issue`
  - 

每类 case 可以定义：

- 默认需要哪些证据
- 哪些 skill 常用
- 哪些风险点高
- 哪些人工队列负责
  - 

### 价值

这一步代替传统平台的“意图树 + 场景流程起点”。一旦前期将每个顾客的 case 搭建好，那后续的体验将会非常丝滑。

## 16.2 Agent Loop / Strategy 配置

### 目标

配置 Agent 在不同 case 下的循环策略，而不是固定流程。

### 可以配置的内容

#### A. Loop 入口策略

- 新 case 进入时先做什么
- 是否优先历史 case 匹配
- 是否先做风险识别
- 是否先做知识召回
- 是否先做身份验证
  - 

#### B. 澄清策略

- 什么条件下提澄清问题
- 一次最多问几个问题
- 是否优先问“最小必要信息”
- 哪些信息可延后收集
- 哪些信息必须在动作前确认
  - 

#### C. Action 选择策略

- 哪类 case 优先检索知识
- 哪类 case 优先查 skill
- 哪类 case 必须人审
- 哪类 case 可并行调用多个 skill
- skill 与 retrieval 的优先级
  - 

#### D. Continue / Stop 条件

- 什么时候视为已解决
- 什么时候进入 waiting_user
- 什么时候进入 waiting_human
- 什么时候重试
- 什么时候 blocked
- 最多循环几轮
- 最大工具调用次数
- 最大澄清轮数
  - 

#### E. Replan 策略

- skill 返回冲突结果时怎么办
- 检索结论和 API 结论冲突时怎么办
- 人工反馈和 Agent 判断冲突时怎么办
- 是否允许改写当前计划
- 是否需要升级更高优先级 case
  - 

### 价值

传统平台配的是“流程节点路径”，  

我们配的是“Agent 在什么检查点做什么判断”。

## 16.3 Skill Registry / Skill Builder

### 目标

把客户侧各种内部系统、第三方 API、脚本能力、审批动作标准化成 Agent 可调用的 skills。

### 每个 skill 建议可配置：

- Skill 名称
- 描述
- 适用 case 类型
- 输入 schema
- 输出 schema
- 调用方式（API / webhook / script / db / connector）
- 权限等级
- 风险等级
- 超时策略
- 重试策略
- 幂等性
- 是否有副作用
- 是否需要用户确认
- 是否需要人工审批
- 失败 fallback
- 可观测字段
- 示例输入输出
  - 

### 可视化管理能力

- skill 注册
- skill 测试台
- skill mock
- skill 发布版本
- skill 调用日志
- skill 成功率 / 延迟监控
- skill 权限绑定
  - 

### 价值

传统平台只是“接一个 API 节点”；  

我们要做的是“搭建一个 Agent 可组合调用的能力注册中心”。

## 16.4 Retrieval Studio / Knowledge Configuration

### 目标

不是简单上传文档，而是配置 Agent 如何从多种知识源中获得证据。

### 需要支持的知识源类型

- FAQ / help center
- SOP / runbook
- markdown 文档
- 产品公告
- changelog
- 代码仓库
- 配置仓库
- JSON / YAML / SQL 规则文件
- 错误码字典
- 历史 resolution 模板
  - 

### 检索策略配置

#### A. BM25 配置

- 索引范围
- 分词策略
- 权重策略
- 标题/正文权重
- 精确匹配 boost
  - 

#### B. Vector RAG 配置

- 切片大小
- overlap
- embedding 模型
- 多语言策略
- top-k
- rerank 模型
- 相似度阈值
  - 

#### C. grep / code search 配置

- 可检索仓库范围
- 文件类型白名单
- 路径优先级
- 正则规则
- 结构化键值搜索
  - 

#### D. Source priority 配置

- FAQ 优先还是 SOP 优先
- 代码/配置是否高优先
- 哪些源只作参考
- 哪些源可作为高可信证据
  - 

#### E. Citation / Evidence 配置

- 回复是否展示来源
- 是否保留证据引用
- 冲突证据如何标记
- 哪些内容只能内部使用不可直接对用户展示
  - 

### 价值

传统低代码平台的“知识库”是答题库；  

我们的 Retrieval Studio 是 Agent 的事实与证据供给系统。

## 16.5 UX / Interaction Builder

这是非常重要但容易被忽略的一块。  

因为 Agent 不是只输出文字。

### 目标

配置 Agent 在不同节点如何与用户交互。

### 需要支持的交互组件

- 文本消息
- 单选 / 多选卡片
- 表单卡片
- 文件上传请求
- 凭证上传引导
- 用户确认卡片
- 处理中状态
- 分阶段进度条
- 结果摘要卡
- 阻塞说明卡
- 后续建议卡
  - 

### 可配置项

- 哪类 case 默认用哪种交互模式
- 缺少某类证据时展示什么卡片
- skill 执行中如何展示进度
- 等待人工时如何提示用户
- 结果返回时用简版还是详版
- 是否展示阶段性计划
- 用户否认时如何重开澄清
  - 

### 价值

传统平台后台多是“话术编辑器”；  

我们需要的是“任务型交互设计器”。**而这些交互方式都可以由我们的UI/UX 团队去在后台设计并提供给客户使用。**

## 16.6 Human-as-a-Tool 配置中心

### 目标

把人工协作标准化成 Agent 可调用的结构化资源。

### 可配置内容

- 人工队列定义
- 角色分组
- SLA
- 优先级规则
- 超时策略
- 升级策略
- Agent 到人工的摘要模板
- 人工返回结果模板
- 人工任务字段约束
- 回流触发动作
- 人工不可见 / 可见信息范围
  - 

### 示例

可以配置：

- 财务队列
- 风控队列
- 支付渠道队列
- 二线技术支持
- VIP support
  - 

每个队列定义：

- 接收什么类型问题
- 需要看到哪些 evidence
- 响应时限
- 回答格式
- 是否允许 free text
- 是否需要二次确认
  - 

### 价值

传统平台中的“转人工”只是路由；  

我们的后台要支持“人工任务建模”。

## 16.7 Policy / Guardrail 配置中心

### 目标

控制 Agent 的可执行边界，而不只是限制回答话术。

### 可配置内容

- 高风险 case 类型
- 敏感信息规则
- 是否允许自动执行某类操作
- 是否必须用户确认
- 是否必须人工审批
- 多语言合规限制
- 账号/资金类动作权限
- 红线关键词
- 风险升级规则
- 安全模式响应模板
  - 

### 价值

传统平台的 guardrail 主要是“别乱说”；  

我们的 guardrail 要做到“别乱做”，重要的敏感任务一定要和人工确认，并由系统强制兜底。

## 16.8 Memory / Resume 配置

### 目标

定义 Agent 如何记忆和恢复 case。

### 可配置内容

- case 记忆有效期
- 哪些 evidence 可复用
- 哪些字段需要重新确认
- 历史 case 匹配窗口
- resume 提示逻辑
- summary 压缩策略
- 是否保留 action trace
- 哪些内容可进入长期记忆
- 哪些内容必须清除
  - 

### 价值

传统平台记的是上下文；  

我们要记的是“问题处理进度”。

## 16.9 Evaluation / Simulation 配置

这个模块对平台落地非常关键。

### 目标

帮助交付和运维人员验证 Agent 是否真的按预期工作。

### 需要支持

- case 回放
- 对话重跑
- tool trace 查看
- skill success/failure 分析
- retrieval 命中分析
- 人工任务回流分析
- 解决率分析
- 失败 case 聚类
- prompt / strategy A/B test
- 模拟用户测试
  - 

### 价值

传统低代码平台更多靠人工点流程测；  

我们要做的是 Agent 行为评估台。

## 16.10 Observability / Agent Ops

### 目标

支持线上运行监控和持续优化。

### 需要监控的对象

- case 解决率
- 平均澄清轮数
- tool 调用成功率
- retrieval 有效命中率
- human task 周转时间
- blocked case 数量
- risk case 数量
- 用户中断率
- Agent loop 超限率
- 重规划频率
  - 

### 价值

这决定平台不是 demo，而是可运营系统。

## 16.11 Versioning / Publish / Environment 管理

### 目标

让配置、skill、策略、知识源能版本化和灰度发布。

### 需要支持

- 草稿 / 测试 / 生产环境
- agent 策略版本
- skill 版本
- prompt 版本
- 知识源版本
- 配置 diff
- 回滚
- 灰度发布
- 沙箱测试
  - 

### 价值

我们的后台必须是工程化的。
