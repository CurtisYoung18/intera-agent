1. 背景与目标

Intera Agent Loop 通过 SSE 流式输出，具备 thinking chain、多 skill 串联执行、等待用户输入等能力。当接入 LiveChat 作为前端 widget 时，需要一个 Bridge 服务在 Intera 的 SSE 事件流与 LiveChat Bot Agent API 之间做翻译，使以下体验成为可能：

  • 用户在 LiveChat widget 内看到 Intera 实时执行状态（哪个 skill 在跑）
  • 选项交互（propose_interaction）映射为 LiveChat 富消息
  • 表单收集（request_user_input）在 widget 内或近 widget 完成
  • 人工升级（create_human_task）无缝转接 LiveChat 真实客服

4. 思维链 & Skill 状态播报

✅ 已确定：方案 B — 实时状态文本流

每触发一个 skill，Bridge 向 LiveChat 发送一条系统风格的状态消息，让用户实时感知 Intera 的处理进度，最后输出最终回复。

SSE 事件 → LiveChat 消息 映射

Intera SSE 事件发送内容消息样例
tool_executingskill 触发提示🔍 正在查阅知识库…
tool_executing (kb_hybrid_retrieve)知识库搜索提示📚 正在检索相关知识…
tool_executing (create_human_task)转接准备提示👤 正在为您转接人工客服…
skill_result（静默，结果内嵌在最终回复）—
form_request逐问收集或 In-Chat App 触发📋 需要几个信息，请逐步回答…
escalated转接完成通知✅ 已为您转接客服，预计等待 X 分钟
policy_blocked策略提示⚠️ 此问题需要进一步核实…
message_stop（无消息，流结束）—

5. 表单输入策略

✅ 已确定：混合路由（方案 C）

LiveChat 原生不支持表单输入字段，通过如下路由规则在 widget 内最大化完成度：

条件路由方式Intera 侧接收格式
字段数 ≤ 3，均为 text/select 类型 逐问对话 Bot 逐字段发问，用 quick_replies 处理 select，文字回复处理 text Bridge 累积每轮回答 → 收齐后一次性注入为 request_user_input tool result
字段数 > 3，或含 file/textarea/date In-Chat App flip card 触发翻转表单卡片，用户在 widget 内填写 In-Chat App 通过 send_event 发送结构化 JSON properties → Bridge 直接注入 tool result

In-Chat App 表单提交格式（规范）

// LiveChat In-Chat App 发送（不经过 LLM）
window.LiveChatWidget.call("send_event", {
  type: "intera_form_submit",
  properties: {
    skill_id: "request_user_input",
    fields: [
      { id: "order_id",  value: "ORD-20240512" },
      { id: "reason",    value: "商品与描述不符" },
      { id: "photo_url", value: "https://..." }
    ]
  }
})

// Bridge 侧接收后直接构造 tool result，注入 loop
// 用户在 LiveChat 界面不会看到这条原始事件
关键原则：表单提交事件永远不走 LLM 解析路径。Bridge 检测到 type: "intera_form_submit" 后，直接将 properties.fields 注入为 skill tool result，绕过用户消息队列。

6. 数据流：结构化注入原则

✅ 已确定：Bridge 层结构化，LLM 永不解析表单
1
用户在 LiveChat widget 发送消息 / 点击按钮 / 提交 In-Chat App
↓
2
LiveChat webhook incoming_event 推送到 Bridge
↓
3
Bridge 路由判断：
• event.type = "message" → 普通用户消息 → 送入 Intera user turn
• event.type = "intera_form_submit" → 解析 JSON → 注入 skill tool result
• event.postback.id 存在 → 解析 option id → 注入 interaction tool result
↓
4
Intera loop 处理，SSE 事件流回 Bridge
↓
5
Bridge 将 SSE 事件翻译为 LiveChat send_event 调用（状态消息 + 最终回复 + 富消息）

消息类型分类

来源格式Bridge 处理送入 Intera
普通文字消息自然语言原样转发user turn
quick_replies 点击postback.id + 文本取 id，跳过文本interaction tool result
逐问对话每轮回答自然语言累积到字段缓冲区字段收齐后注入 tool result
In-Chat App 表单结构化 JSON event解析 properties.fields直接注入 tool result

7. propose_interaction 渲染方案

🔄 决策中

propose_interaction skill 支持 label + description + 可选 inputType=text（点选后需追加文字输入）。三种渲染方案对比：

方案LiveChat 实现description 可见inputType=text开发成本
A. 原生 quick_replies LiveChat 内置模板 ❌ 不支持 ❌ 需额外一问 ⭐ 最低
B. Cards Carousel LiveChat cards 模板，每选项一张卡 ✅ 支持 ❌ 无法内嵌输入 ⭐⭐ 中
C. In-Chat App 选项列表 自定义 In-Chat App ✅ 支持 ✅ 可内嵌输入框 ⭐⭐⭐ 较高（与表单 App 共用框架）
推荐策略（待确认）：
  • 无 description + 无 inputType=text → 方案 A（quick_replies，零成本）
  • 有 description + 无 inputType=text → 方案 B（cards carousel）
  • 有 inputType=text 的选项 → 方案 C（In-Chat App，与表单 flip card 共用一套 App）

8. Bridge 架构（草案）

🔄 位置待确认：内嵌 apps/chat vs 独立服务

核心职责

  • 接收 LiveChat webhooks（incoming_chat, incoming_event, chat_transferred）
  • 维护 chat_id → Intera session 映射
  • 路由消息类型（自然语言 vs 结构化表单 vs interaction 选择）
  • 订阅 Intera SSE 流，翻译为 LiveChat send_event 调用
  • 管理逐问表单字段缓冲区（含超时处理）
  • 在 create_human_task 时调用 transfer_chat + update_chat_properties

关键状态机

chat 状态:
  idle          → 等待用户消息
  thinking      → Intera loop 运行中
  waiting_form  → 逐问收集中（字段缓冲区活跃）
  waiting_ia    → 等待 In-Chat App 表单提交
  waiting_choice → 等待 quick_replies 点击
  transferred   → 已转接真实客服
