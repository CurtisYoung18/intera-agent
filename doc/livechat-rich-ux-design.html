1. 背景与目标

Intera Agent Loop 通过 POST /api/messages 提供 SSE 流式接口，具备 thinking chain、多 skill 串联执行、等待用户输入等能力。接入 LiveChat 作为前端 widget 时，需要一个 Bridge 层在 LiveChat Bot Agent API 与 Intera 现有接口之间做翻译，使以下体验成为可能：

  • 用户在 LiveChat widget 实时看到 Intera 执行状态（哪个 skill 在跑）
  • 选项交互（propose_interaction）映射为 In-Chat App 富选项列表
  • 表单收集（request_user_input）通过 In-Chat App 在 widget 内完成
  • 人工升级（create_human_task）无缝 transfer 给 LiveChat 真实客服
  • Agent 最终文本回复推送为 LiveChat 消息
Bridge 定位：Bridge 是一个薄适配器，只调用现有的 /api/messages 接口，不接触 loop 内部实现。现有 API 的所有能力（session 管理、memory、case 状态等）原封不动复用。

4. 思维链 & Skill 状态播报

✅ 已确定：方案 B — 实时状态文本流

每当 Intera loop 触发一个 skill（SSE tool_executing 事件），Bridge 向 LiveChat 发送一条状态消息，让用户实时感知处理进度，最后输出最终回复。

5. 交互响应：表单 & 选项

✅ 已确定
重要：触发条件是 Intera 调用对应 skill，与用户输入内容无关。
Bridge 只看 SSE 事件类型决定渲染方式，不做任何"字段数量 / 内容长度"判断。

5.1 propose_interaction → In-Chat App OptionList

当 Bridge 收到 interaction_proposed SSE 事件，向 LiveChat 发两个动作：

  1. 一条普通消息：问题文本（例如"您希望如何处理？"）
  2. 一个 intera_widget_payload 自定义事件，触发 In-Chat App 渲染 OptionList 视图
// Bridge 发给 LiveChat 的 widget payload 事件
send_event({
  type: "intera_widget_payload",
  properties: {
    kind: "propose_interaction",
    caseId: "case_xxx",
    options: [
      { id: "refund", label: "申请退款", description: "3-5个工作日退至原账户" },
      { id: "exchange", label: "更换商品", description: "免费换货，2-3天重发" },
      { id: "other", label: "其他问题", inputType: "text", inputPlaceholder: "请描述..." }
    ]
  }
})

In-Chat App 收到事件后渲染 OptionList。用户点选后，App 发送：

// In-Chat App → LiveChat (send_event)
window.LiveChatWidget.call("send_event", {
  type: "intera_interaction_submit",
  properties: { caseId: "case_xxx", optionId: "refund", input: "" }
})

Bridge 收到 webhook，调用现有接口：

// Bridge → POST /api/messages（现有接口，原生支持）
{
  interactionResult: { caseId: "case_xxx", optionId: "refund" },
  customerId: "...",
  userId: "..."
}

5.2 request_user_input → In-Chat App FormCard

当 Bridge 收到 form_request SSE 事件，触发 In-Chat App 渲染 FormCard 视图（含翻转动画）：

// Bridge 发给 LiveChat 的 widget payload 事件
send_event({
  type: "intera_widget_payload",
  properties: {
    kind: "request_user_input",
    caseId: "case_xxx",
    fields: [
      { id: "order_id", type: "text", label: "订单号", required: true },
      { id: "reason",   type: "select", label: "退款原因", options: ["商品与描述不符", "未收到货"] },
      { id: "photo",    type: "file",   label: "上传凭证", required: false }
    ]
  }
})

用户填写提交后，App 发送：

// In-Chat App → LiveChat (send_event)
window.LiveChatWidget.call("send_event", {
  type: "intera_form_submit",
  properties: {
    caseId: "case_xxx",
    answers: { order_id: "ORD-0512", reason: "商品与描述不符", photo: "https://..." }
  }
})

Bridge 收到 webhook，调用现有接口：

// Bridge → POST /api/messages（现有接口，原生支持）
{
  formResult: {
    caseId: "case_xxx",
    answers: { order_id: "ORD-0512", reason: "商品与描述不符" }
  },
  customerId: "...",
  userId: "..."
}
零侵入：formResult 和 interactionResult 是 /api/messages 已有的原生参数（见 route.ts 第 310–345 行），Bridge 直接使用，不需要改动 loop 任何代码。

6. 文本输出策略

✅ 已确定：缓冲后一次性推送

LiveChat Bot Agent API 不支持流式更新消息（没有"更新已有消息"机制），因此：

1
SSE text_delta 事件（x N 次）→ Bridge 追加到文本缓冲区，不发 LiveChat
↓
2
SSE message_stop 事件 → 缓冲区内容完整 → Bridge 调用 send_event 一次性推送完整回复

用户感知：状态消息（skill 播报）一条一条实时出现，最终回复整段 appear，无中间卡顿。

若未来 LiveChat 支持消息更新（update_event），可改为边收 text_delta 边更新，用户体验升级为流式打字效果，Bridge 侧只改发送策略，其余不变。

核心逻辑（伪代码）

// /api/livechat/webhook/route.ts
async function handleLiveChatEvent(event: LiveChatEvent, chatId: string) {
  const { customerId, userId, caseId } = await sessionStore.get(chatId)

  // 按事件类型组装 /api/messages 的 body
  let body: MessagesBody
  if (event.type === 'intera_form_submit') {
    body = { formResult: { caseId, answers: event.properties.answers }, customerId, userId }
  } else if (event.type === 'intera_interaction_submit') {
    body = { interactionResult: { caseId, optionId: event.properties.optionId, input: event.properties.input }, customerId, userId }
  } else {
    body = { message: event.text, chatId, customerId, userId }
  }

  // 调现有接口（SSE 流）
  const stream = await fetch('/api/messages', { method: 'POST', body: JSON.stringify(body) })

  // 消费 SSE，翻译成 LiveChat 操作
  await consumeSSEAndPushToLiveChat(chatId, stream)
}

会话状态机

Bridge 为每个 LiveChat chat_id 维护一个轻量状态：

idle
→
thinking
→
waiting_choice
→
thinking
→
waiting_form
→
thinking
→
transferred

任何状态下收到新用户消息（非表单/交互事件）→ 重新触发 loop，防止用户因等待超时重发后卡死。

Session Store 结构

// chatId → session context（内存 Map，多实例时换 Redis）
interface BridgeSession {
  customerId: string
  userId:     string
  caseId:     string       // 当前活跃的 Intera case，用于 formResult / interactionResult
  state:      BridgeState  // idle | thinking | waiting_choice | waiting_form | transferred
  textBuffer: string       // 累积 text_delta，message_stop 时一次性 push
}
chatId 已是 /api/messages 原生参数。Bridge 传入 chatId: livechat_chat_id，Intera 侧自动把消息历史绑定到该 chat，无需额外 session 映射机制。

8. In-Chat App 开发

✅ 已确定：一期实现，放在 apps/chat 内

注册方式

在 developers.livechat.com 注册为私有 App（不上 Marketplace），安装到自己的 LiveChat Organization：

  1. My Apps → Create new app
  2. Placement: Chat Widget
  3. App URL: https://chat.intera.io/livechat-widget（apps/chat Next.js 路由）
  4. 安装到 LiveChat Organization → 完成

动态内容机制

In-Chat App URL 是固定的，内容由 Bridge 通过 intera_widget_payload 自定义事件实时注入：

// In-Chat App 监听 Bridge 推送的 payload
window.LiveChatWidget.on("new_event", (event) => {
  if (event.type === "intera_widget_payload") {
    const { kind, ...payload } = event.properties
    if (kind === "propose_interaction") renderOptionList(payload)
    if (kind === "request_user_input")  renderFormCard(payload)
  }
})

同一个 App 两种视图，LLM 生成什么字段/选项，Bridge 就推什么 payload，App 动态渲染，无需重新注册或修改 App URL。

两种视图职责

视图对应 skill渲染内容提交事件
OptionList propose_interaction 选项列表，含 label + description + 可选文字输入框 intera_interaction_submit
FormCard request_user_input 翻转卡片表单，支持 text / select / file / date 等全部字段类型 intera_form_submit
