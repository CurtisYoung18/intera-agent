## 0.0 集成模型：Agent 账号接管（不是 bot）⚠️ 重要前提

> 用户确认：采用的是 **GPTBots 式「人工 agent 账号被 AI 接管」**模型（参考 https://www.gptbots.ai/zh_CN/docs/tutorial/bot/integration/livechat），**不是 LiveChat Bot agent**。这条改变了①②两个问题的根因框架，先读懂再往下看。

GPTBots 模型的关键点（适用于 Intera）：

1. **身份**：用某个**人工客服 agent 账号**的 **PAT（Personal Access Token：Account ID + Token）**做鉴权（`Authorization: Basic base64(accountId:token)`）。AI 以**这个具名 agent 的身份**回复——客户看到的是该客服，不是"机器人"。
2. **App + webhook**：在 Developer Console 建一个 server-side app（拿 Client Id/Secret 做安装授权），再加 **chat webhooks**（注意是 chat webhooks，**不是 app webhooks**），订阅 `incoming_event` + `incoming_chat`，并**勾选 `chat_presence_user_ids`**（webhook 会带"当前哪些 agent 在这个 chat 里"）。Private Installation → Install。
3. **路由/分组**：建一个 Group，把"被 AI 接管的 agent"设为 **Primary**、人工客服设为 **Backup**，并让 AI agent **`accepting_chats`（在线接单）**。这样新会话**先路由给 AI agent**，AI agent 因此成为会话成员，`send_event` 才能发出。
4. **人工接管**：人工一旦接手，AI 应停（靠 `chat_presence_user_ids` 判断人工在场）。

**对 Intera 现状的影响**：现有代码把它当成"无差别 license webhook + 单 token 直发"在用——**既没管 agent 的接单状态/在场，也不读 `chat_presence_user_ids`**。这正是文字打不通 + 多 AI 抢答的核心。

## 0. TL;DR — 文字消息打不通的真凶（Agent 接管模型下）

按"最可能 → 次要"排序，每条都给了证据与修复点：

| # | 根因 | 证据 | 影响 | 修复 |
|---|---|---|---|---|
| **RC1** | `send_event` 要求**调用方 agent 必须在该 chat 内**。Agent 接管模型下，"在场"靠**路由把会话分给该 agent**（需 `accepting_chats` + Primary）。Intera **不管 agent 接单状态、也不确认自己是否在场就直接 send** → 没分到的会话发不出去。 | [livechat-api.ts:20-42](apps/chat/lib/livechat/livechat-api.ts:20) 无 presence/路由处理；全仓库无 `set_routing_status` | **AI 生成了回复但发不出去**（403 not present） | ①确保 AI agent `accepting_chats`+Primary（文档②）；②webhook 按 `chat_presence_user_ids` 只处理"我在场"的会话（见 RC0）；③兜底给 `send_event` 加 `ignore_requester_presence:true` |
| **RC0** | **不读 `chat_presence_user_ids`**：对每个 `incoming_event` 都无脑响应，不判断这条会话是不是分给"我"这个 agent。 | [webhook/route.ts:66-112](apps/chat/app/api/livechat/webhook/route.ts:66) 收到 message 就 `handleIncomingEvent`，从不看在场者 | 既会对没分给自己的会话 send 失败（RC1），又会和别的 agent/集成抢答（问题②） | webhook 注册时勾 `chat_presence_user_ids`；只在 `agentAccountId ∈ chat_presence_user_ids` 时处理；人工也在场时让位 |
| **RC2** | `X-Region` 写死 `fra`，但 LiveChat 默认数据区是 `dal`。PAT 也带区。区错 → API 解析不到你的数据。 | [livechat-api.ts:31](apps/chat/lib/livechat/livechat-api.ts:31) `'X-Region': 'fra'` | 整条 API 调用 404/鉴权失败 | region 从 PAT/token 前缀解析（`dal:`/`fra:`）或存进 config 列 |
| **RC3** | 鉴权用 PAT Basic（`base64(accountId:token)`），但现在靠"长度>60 且像 base64"猜，易误判。 | [livechat-api.ts:14-18](apps/chat/lib/livechat/livechat-api.ts:14) `detectAuth` | 401 Unauthorized | config 显式存 `authType='basic'` + 用 `accountId`/`token` 正确拼 Basic |
| **RC4** | **无 author 过滤**：AI 以 agent 身份发的消息会再次触发 `incoming_event`（author=该 agent）→ AI 回自己 → 死循环。 | [webhook/route.ts:52](apps/chat/app/api/livechat/webhook/route.ts:52)、[[customerId]/route.ts:64](apps/chat/app/api/livechat/webhook/[customerId]/route.ts:64) 只取 `author_id`，从不比较 | 回声循环、重复计费 | 存 `agentAccountId`，webhook 里 `author_id === agentAccountId` 直接 return |
| **RC5** | `incoming_chat` 用空文本 `text:''` 调 bridge，`/api/messages` 直接返回 `Message is required`。 | [webhook/route.ts:115-120](apps/chat/app/api/livechat/webhook/route.ts:115)、[messages/route.ts:398-406](apps/chat/app/api/messages/route.ts:398) | 新会话开场什么都不发（不致命，但噪声大、欢迎语无） | `incoming_chat` 改为"欢迎语 / 仅建 session"，不要喂空消息进 loop |
| **RC6** | config 缺失或 `enabled=false` 时 webhook **静默丢弃**，排障无信号。 | [webhook/route.ts:61-64](apps/chat/app/api/livechat/webhook/route.ts:61)、[[customerId]/route.ts:27-30](apps/chat/app/api/livechat/webhook/[customerId]/route.ts:27) | "什么都没发生"且无日志 | 确认 `api` 客户已存 LiveChatConfig 且 `enabled=true`；加日志 |
| **RC7** | bridge 回调 `/api/messages` 的内部地址默认 `localhost:3000`，Railway 上若未配置可能打不通。 | [bridge.ts:19-22](apps/chat/lib/livechat/bridge.ts:19) | `engine_unreachable`，发"系统暂时无法处理" | 部署环境必须设 `INTERNAL_CHAT_API_URL` |

> **结论**：本模型下 **RC1+RC0+RC2** 是文字打不通的主因——会话没路由给 AI agent（或没确认在场）+ 区写死。先做：①把 AI agent 设 `accepting_chats`+Primary（文档②）；②webhook 按 `chat_presence_user_ids` 过滤；③region 改对。RC4 是"多 AI 抢答"的代码侧成因之一（平台侧见文档②）。`ignore_requester_presence:true` 作为兜底仍建议加，但**正解是靠路由让 agent 真正在场**。

### 2.0 确认 agent 接管链路（本模型最关键）

- [ ] 用来接管的**人工 agent 账号**已建，并拿到它的 **PAT（Account ID + Token）**。
- [ ] 该 agent 在一个 **Group** 里被设为 **Primary**，人工客服为 **Backup**。
- [ ] 该 agent **`accepting_chats`（在线接单）**——否则新会话不会路由给它，`send_event` 必然 403。
  ```bash
  # 查接单状态
  curl -s -X POST https://api.livechatinc.com/v3.5/agent/action/list_routing_statuses \
    -H "Authorization: Basic <base64(accountId:token)>" -H "X-Region: <dal|fra>" \
    -H "Content-Type: application/json" -d '{}'
  # 设为接单
  curl -s -X POST https://api.livechatinc.com/v3.5/agent/action/set_routing_status \
    -H "Authorization: Basic <base64(accountId:token)>" -H "X-Region: <dal|fra>" \
    -H "Content-Type: application/json" \
    -d '{"status":"accepting_chats","agent_id":"<agent_email_or_id>"}'
  ```
- [ ] webhook 用的是 **chat webhooks**（不是 app webhooks），订阅 `incoming_event`+`incoming_chat`，**且勾了 `chat_presence_user_ids`**（payload 才会带在场 agent 列表，供 RC0 过滤）。
- [ ] 记下该 agent 的 **id/email**（= `agentAccountId`），webhook 自过滤和在场判断都要用。

### 2.1 确认数据区 region（dal vs fra）

LiveChat 有两个数据中心：**dal（美国，默认）**、**fra（欧洲）**。token 字符串本身带区前缀（`dal:xxx` / `fra:xxx`）。

```bash
# 方法 A：直接看 token 前缀（如果是 Bearer token / 解码后的 PAT）
#   dal:... → region=dal ；fra:... → region=fra

# 方法 B：用 accounts info 端点验证 token + 拿 organization
curl -s https://accounts.livechat.com/v2/info \
  -H "Authorization: Bearer <你的 token>"

# 方法 C：直接探一个只读 action，两个区各打一次，看哪个返回 200
for R in dal fra; do
  echo "== region=$R =="
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST "https://api.livechatinc.com/v3.5/agent/action/list_agents" \
    -H "Authorization: <Bearer 或 Basic> <token>" \
    -H "X-Region: $R" \
    -H "Content-Type: application/json" \
    -d '{}'
done
```

返回 200 的那个区就是答案。**当前代码写死 `fra`，如果你的账号是 `dal`（默认），这就是 bug。**

### 2.2 确认鉴权类型（本模型 = PAT Basic）

- **Personal Access Token (PAT)** → `Authorization: Basic base64(accountId:token)` ← **本模型用这个**（接管 agent 账号）
- （对照）Bot Access Token → `Authorization: Bearer <token>`（本模型不用）

最近提交（c754ce2）已提到走 PAT Basic Auth。用 2.1 的 curl，Basic header 拼成 `base64(accountId:token)`，能 200 的区就是答案。

### 2.3 确认 PAT scope

`send_event` / `send_typing_indicator` 需要 scope **`chats--all:rw`** 或 **`chats--access:rw`**。少了就 403。创建 PAT 时勾上对应 scope。

### 2.4 确认 LiveChatConfig 已落库且 enabled

```bash

# 或直接查库（生产 Postgres，只读）：
#   select customer_id, license_id, enabled, length(bot_access_token) from livechat_configs where customer_id='api';
```

`enabled=false` 或这行不存在 → RC6 静默丢弃。

## 3. 代码级修复（按优先级）

### 修复 A（P0，必做）：`send_event` 加 `ignore_requester_presence` + region 可配

**文件**：[apps/chat/lib/livechat/livechat-api.ts](apps/chat/lib/livechat/livechat-api.ts)

LiveChat 的 `send_event`（含 message / rich_message / file / system_message）和 `send_typing_indicator`、`deactivate_chat` 都要求**调用方 agent 是会话成员**。Agent 接管模型下：

- **正解**：让 AI agent `accepting_chats`+Primary，新会话自动路由分给它 → 它就是成员（平台配置见文档②）。
- **兜底（推荐叠加）**：所有这类调用带 `ignore_requester_presence: true`，即使路由边界情况也不至于发不出去。
- 配合**修复 F（RC0 在场过滤）**：只对"分给我"的会话回复，避免对没分到的会话硬发。

把 `lcPost` 改成接受可选 region，并在 send 类 body 里默认带上 presence 覆盖：

```ts
// livechat-api.ts —— 顶部
// 之前：const LC_API_BASE = 'https://api.livechatinc.com/v3.5/agent/action'
const LC_API_HOST = 'https://api.livechatinc.com/v3.5/agent/action'

// region 改为参数，默认 dal（LiveChat 默认区，而不是 fra）
async function lcPost(
  action: string,
  body: unknown,
  botAccessToken: string,
  licenseId: string,
  region: string = process.env.LIVECHAT_REGION ?? 'dal',   // ← 可配，默认 dal
): Promise<void> {
  const res = await fetch(`${LC_API_HOST}/${action}`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: detectAuth(botAccessToken),
      'X-Region': region,                                   // ← 不再写死 fra
    },
    body: JSON.stringify({ ...(body as Record<string, unknown>), license_id: licenseId }),
  })
  if (!res.ok) {
    const text = await res.text()
    const err = new Error(`LiveChat API ${action} failed (${res.status}): ${text}`) as Error & { code?: string }
    if (res.status === 401) err.code = 'TOKEN_EXPIRED'
    if (res.status === 403) err.code = 'NOT_IN_CHAT'        // ← 新增：成员校验失败的典型码
    if (res.status === 429) err.code = 'RATE_LIMITED'
    throw err
  }
}
```

`send_event` body 加 `ignore_requester_presence`：

```ts
export async function sendTextMessage(
  chatId: string, text: string, botAccessToken: string, licenseId: string, region?: string,
): Promise<void> {
  await lcPost('send_event', {
    chat_id: chatId,
    event: { type: 'message', text, visibility: 'all' },
    ignore_requester_presence: true,          // ← 关键
  }, botAccessToken, licenseId, region)
}
```

> 对 `sendWidgetPayload` / `sendQuickReplies` / `sendCard` / `sendCarousel` / `sendImage` / `sendSystemMessage` 都加同一个字段。`send_typing_indicator`、`transfer_chat` 同理（typing 也要求成员，transfer 本身就是改成员）。

> **更优雅的做法**：把 `ignore_requester_presence: true` 收敛到 `lcPost` 内部，对 `action === 'send_event' || action === 'send_typing_indicator'` 自动注入，省得每个函数都加。

### 修复 F（P0）：按 `chat_presence_user_ids` 只处理"分给我"的会话（RC0，本模型核心）

**前提**：webhook 注册时勾了 `chat_presence_user_ids`（§2.0），payload 才带在场 agent 列表。

**文件**：两个 webhook 路由，分发前判断。

```ts
// LiveChat 在 payload 里给出当前 chat 的在场 agent id 列表（字段名以实际 payload 为准，
// 常见于 payload.additional_data.chat_presence_user_ids 或 payload.chat_presence_user_ids）
const presentIds = ((body.additional_data as Record<string, unknown>)?.chat_presence_user_ids
  ?? (body.payload as Record<string, unknown>)?.chat_presence_user_ids
  ?? []) as string[]

// 只在"我（被接管 agent）在场"时响应；否则这条会话不归我管 → 跳过
if (config.agentAccountId && presentIds.length && !presentIds.includes(config.agentAccountId)) {
  return NextResponse.json({ ok: true, skipped: 'not_my_chat' })
}

// 可选的人工让位：如果有人工 agent 也在场（人工已接管），AI 退场
// if (presentIds.some(id => HUMAN_AGENT_IDS.includes(id))) return ...
```

> 这同时解决两件事：① 不再对"没分给我"的会话硬 `send_event`（消除 RC1 的 403 来源）；② 多集成/多 agent 场景下，**只有被分到会话的那个 agent 的集成会响应** → 这是"多 AI 抢答"在代码侧的真正解药（配合文档②的 Primary/Backup 路由）。
> 落地前**务必抓一份真实 webhook payload**确认 `chat_presence_user_ids` 的确切字段路径。


改为二选一：

- **方案 1（推荐）**：只建 session + 发一句欢迎语，不进 agent loop。
  ```ts
  if (action === 'incoming_chat') {
    await upsertSession({ chatId, customerId, userId, caseId: generateCaseId(), state: 'idle', textBuffer: '' })
    // 可选：发个固定欢迎 card / 文本
    await sendTextMessage(chatId, '您好，我是智能客服，请描述您遇到的问题～', config.botAccessToken, config.licenseId, config.region).catch(() => {})
    return NextResponse.json({ ok: true })
  }
  ```
- **方案 2**：如果 `incoming_chat` 的 payload 里带了首条 message（LiveChat 会在 `payload.chat.thread.events` 里带初始事件），把那条真实文本提取出来再喂 loop。

> 顺带：bridge 的 `buildMessagesBody` 对空 text 也应防御——空字符串别发起 loop。

### 修复 E（P1）：可观测性 —— 别再静默吞

webhook 里 config 缺失 / disabled / 签名失败时，至少打一条带 `customerId`、`action`、`chatId` 的 warn 日志（注意不要打 token）。bridge 里 `send*` 抛错时已 `console.error`，但建议把 `NOT_IN_CHAT` / `TOKEN_EXPIRED` 单独计数，方便定位是 RC1 还是 RC2/RC3。

## 4. 改完后的端到端联调步骤

1. 跑 §2 的 agent/region/auth 探测：AI agent `accepting_chats`+Primary；拿到正确 `region`/`authType`/`accountId`/`agentAccountId`，写进 `api` 客户的 LiveChatConfig（console 或直接改库）。
2. 部署设好 `INTERNAL_CHAT_API_URL`、`LIVECHAT_WEBHOOK_SECRET`（或用 per-customer webhookSecret 列）。
3. 在 LiveChat Developer Console 确认该 app 的 **chat webhooks**：
   - 订阅了 `incoming_event` + `incoming_chat`，**且勾了 `chat_presence_user_ids`**；
   - webhook URL = `https://intera-chat.up.railway.app/api/livechat/webhook/api`；
   - 用了和 config 里一致的 secret。
4. 打开测试页 `/test/livechat`，点聊天气泡，发"你好，我要查一笔充值"。
5. 期望：replying/typing 指示亮 → 几秒后 AI（以 agent 身份）回文字。
6. 若仍无回复，按下面排障表定位。

### 排障对照表

| 现象 | 看哪 | 大概率原因 |
|---|---|---|
| webhook 没收到（LiveChat 后台显示 webhook failing/无调用） | LiveChat Developer Console webhook 日志 | URL/secret 错；app 未启用 webhook |
| webhook 收到但 bridge 没动 | 服务日志 `[Webhook]` | RC6 config 未 enabled；签名 401；被 dedup |
| bridge fetch /api/messages 失败 | 日志 `engine_unreachable` | RC7 `INTERNAL_CHAT_API_URL` 错 |
| agent 跑完但用户没收到字 | 日志 `[Bridge] action failed: send_text` + 状态码 | **RC1**（403：agent 没在场/没接单）或 **RC2**（区错 404）或 **RC3**（401 PAT 拼错） |
| 对没分给自己的会话也在发、且常 403 | webhook 未过滤 | **RC0** 没读 `chat_presence_user_ids`（修复 F） |
| AI 回了，但紧接着又自言自语 | 日志重复 handleIncomingEvent | **RC4** 自回声，`agentAccountId` 没配/没过滤 |
| 多个不同语气的回复同时出现 | —— | 多 agent/集成抢答：先修复 F 在场过滤，再看**文档 ②**路由 |

## 5. 验收标准（本文档）

- [ ] AI agent `accepting_chats`+Primary；`api` 客户 LiveChatConfig 含正确 `region`/`authType`/`accountId`/`agentAccountId`，`enabled=true`。
- [ ] 测试页发一条文字，AI（以 agent 身份）在数秒内回一条文字，**且不重复、不自我循环**。
- [ ] webhook 按 `chat_presence_user_ids` 过滤：只回"分给自己"的会话（修复 F 生效）。
- [ ] 连续多轮对话上下文正确（同一 chatId → 同一 caseId）。
- [ ] 人为把 token 置错 → 日志能明确报 `TOKEN_EXPIRED` 或 `NOT_IN_CHAT`，而不是"什么都没发生"。
- [ ] `send_event` 调用带 `ignore_requester_presence` 兜底；`X-Region` 来自 config 而非写死。
