一、功能性 Bug（建议优先修）

B1. 图标渲染失败：图标名称以文字形式显示并遮挡卡片标题 Bug

位置：组件 → 流程（Procedure 列表卡片）　/build/components/procedures
现象
每张 Procedure 卡片左侧的大号浅色"水印词"其实是图标名（lock、smartphone、banknote-arrow-down、history），本应渲染为图标却以纯文本显示，并与卡片标题、编号、描述重叠。banknote-arrow-down 换行三行，遮挡最严重。
影响
显得"半成品"，直接削弱产品可信度；重叠文字干扰对 Procedure 标题的快速识别。
改进
解析失败时不应回退成名称文本——要么渲染正确图标，要么显示一个中性占位图标。装饰元素必须置于内容层之下且不可干扰阅读。
前端建议
① 检查图标映射：动态 name 多半未在打包白名单内（如 lucide 的 dynamicIconImports 缺项），补齐映射或改用静态 import map；② fallback 渲染占位 <HelpCircle/> 而非 {name} 字符串；③ 水印层加 position:absolute; z-index:0; pointer-events:none; overflow:hidden，标题层 z-index:1，并对卡片加 overflow:hidden 裁剪。
评级
Bug 高　工作量：小

B2. i18n 翻译键泄漏：未翻译的 key 直接显示给用户 Bug

位置：组件 → 流程 → 打开某 Procedure → 右侧"模拟"面板　/build/components/procedures/<id>
现象
模拟面板中至少有一处标签和一处 placeholder 显示的是 i18n key 本身，而非翻译后的文案。说明对应语言包缺少该键，框架回退成了显示 key。
影响
用户完全看不懂该字段含义；同样严重影响专业观感。这类缺键往往不止一处。
前端建议
① 补齐 zh（及 en）语言包中 procedureEditor.* 缺失条目；② i18n 配置 fallbackLng + parseMissingKeyHandler，缺键时显示更友好的回退文案而非 key；③ 开启 saveMissing/missingKeyHandler 在开发期告警；④ CI 加一条"翻译键完整性"校验，扫描代码中 t('…') 与语言包做 diff，缺键即失败。
评级
Bug 高　工作量：小

二、本地化一致性（全站最普遍的问题）

L1. 中英文混杂，且术语未本地化

位置：全站，尤以 组织设置 / 发布 / 组件首页 最明显
现象
中文界面里大量保留英文术语与整段英文：
· 组织页说明整段英文，且右上"Organization profile / Members and invitations / Permission matrix"与下方"通用/成员/权限"语言不同且功能重复；
· 发布页："Import dry-run 会继续检查 Required secrets、conflicts、unsupported integrations 和 Knowledge refs"；
· 组件首页："把 Brain、Procedures、Tools、Hooks、Knowledge 和 Integrations 收进同一个本地 Build hub…克制 chip"；
· 通用术语 draft / proposal / diff / handoff / brief / compact / trace / memory / scenario 等几乎从不翻译。
影响
对中文交付/运营人员阅读成本高；"克制 chip""Build 壳层"这类直译更让人困惑；专业度受损。
前端建议
① 制定术语表：决定哪些为产品专有名词保留英文（如 Procedure/Hook 可保留并首次出现括注中文），其余一律翻译，并全站统一；② 把所有硬编码文案收进 i18n 资源；③ 删除组织页重复的英文导航，只保留一套（建议中文 Tab）；④ 找一位中文母语者过一遍 microcopy。
评级
高　工作量：中

L2. 同一功能多种叫法 / 标签语言不统一

位置：人工交接页、对话页统计卡
现象
"人工交接"功能在三处叫法不一：左侧导航＝人工交接、页面标题＝人工接管指挥台、页内标签＝人工接管（交接/接管混用）。对话页统计卡标签语言/大小写不一致：会话数、待接手、PROCEDURERUNS（唯独这张全大写英文）。
影响
同义异名让用户怀疑是不是两个不同功能；统计卡视觉不齐。
前端建议
统一为单一术语（建议全用"人工接管"或"人工交接"其一），导航、标题、标签、面包屑共用同一 i18n key；统计卡标签统一走同一套样式与语言。
评级
中　工作量：小

L3. 未翻译的状态串散落各处

位置：Playground 徽章行、发布页
现象
Playground 顶部徽章：图片 Not supported、MEMORY Balanced、HOOKS 4个、TEMP 0.3 中英大小写混排；发布页 1/5 retained、No draft / Awaiting draft、发布人 不可用（"不可用"实为"未记录/无"，措辞误导）。
前端建议
状态枚举统一走 i18n；"retained"译为"已保留 1/5"；"不可用"按真实语义改为"未填写/暂无"；徽章 label 统一为小型大写或中文，二选一。
评级
中　工作量：小

三、信息架构与布局

A1. 试点实验室右栏严重过载

位置：试点实验室 → Pilot 标签，右侧栏　/build/pilot-lab
现象
右栏在一条窄列里依次堆叠：当前上下文 → Pilot 状态 → 提议改动 → Diff 查看器 → 接受并应用 → Scenario 控制（含 20+ 字段、多个需手写的原始 JSON 输入框，如"期望 Tool-call 规则 JSON""期望 Hook 决策 JSON""observed evidence JSON"）。需要大量滚动，且编辑场景与查看状态混在一起。
影响
认知负担高；手写 JSON 对配置人员极不友好、易出错且无即时校验；中间主区却大片留白，空间分配失衡。
前端建议
① 把"Scenario 编写"从右栏抽出，改为独立抽屉/全宽弹层或独立页，并做分步表单（基本信息 → 对话轮次 → 断言期望）；② 原始 JSON 字段换成结构化编辑器（键值/数组 UI）或至少接入带 schema 校验+高亮的 JSON 编辑器（如 CodeMirror + JSON schema），失焦即校验报错；③ 右栏其余分区支持折叠、记忆展开状态；④ 把部分内容移到留白的主区，平衡左右比重。
评级
高　工作量：中–大

A2. 组件首页表格"这里可以做什么"六行文案完全相同

位置：组件首页　/build/components
现象
大脑/流程/工具/钩子/知识库/集成六行，"这里可以做什么"列内容一字不差："在保留共享 Build 壳层、本地导航和各编辑器原有保存/测试流程的前提下，打开 X 控制面。" 该列零信息量，反而占据视觉重心。
前端建议
为每个能力写差异化一句话（如 流程="定义 Agent 处理某类问题的步骤与分支"；钩子="在工具调用前后/回复前插入校验或拦截"）；或去掉该列，改为"能力简介 + 数量徽章（如 12 套 Procedure）+ 打开"。
评级
中　工作量：小

A3. 主编辑区大片空白，核心配置全靠自由聊天

位置：试点实验室 Pilot / Playground
现象
Pilot 与 Playground 中央区域只有一句问候 + 4 个建议 chip，其余大片空白；几乎所有结构化改动都要通过对 "U-Pilot" 自由打字完成。对偏流程化的"交付配置人员"而言，缺少表单/按钮式的直接入口。
前端建议
① 空状态补充引导（"从这里开始""最近改动""常用操作"卡片）；② 为高频操作（新建 Procedure / 加 Hook / 跑 Scenario）提供按钮式快捷入口，点击预填聊天或直接打开对应表单；③ 让聊天与结构化操作并存，而非二选一。
评级
中　工作量：中

A4. 当前 Agent/版本 在同屏重复显示三次

位置：试点实验室
现象
同一屏里"当前 Agent + 版本"出现三处、样式各异：顶部"正在编辑：J1N v1 当前版本▾"、左栏"当前 AGENT J1N v1"、主区标题"当前 Agent / J1N v1"。哪个可切换、哪个只读不清晰。
前端建议
确立单一权威的 Agent/版本切换控件（建议保留顶部"正在编辑"），其余改为弱化的只读上下文或移除；统一交互（可点即下拉，不可点即纯文本）。
评级
低　工作量：小

四、可用性与交互细节

U1. 破坏性操作缺保护；纯图标按钮无标签

位置：组件卡片、Procedure 编辑器顶栏
现象
每张 Procedure 卡片把红色"Delete"与"Open"并排放在卡片底部，易误点（删除是否二次确认待核实）；Procedure 编辑器顶栏的齿轮/垃圾桶/关闭等为纯图标按钮，无文字标签或 tooltip，含义需猜。
前端建议
① 删除等危险操作移入卡片"⋯ 更多"菜单，或保留但必须二次确认弹窗（输入名称/再次点击）；② 所有图标按钮补 aria-label + hover tooltip；③ 危险按钮用危险色但降低视觉权重（非主操作）。
评级
中　工作量：小

U2. 禁用控件无原因提示

位置：Playground 顶部"导出试跑评审副本"
现象
"导出试跑评审副本"为置灰禁用态，但没有任何说明为何不可用、需满足什么条件。
前端建议
禁用按钮加 tooltip 说明启用条件（如"需先完成一轮运行时测试"）；条件满足后自动启用。
评级
低　工作量：小

U3. "创建/派生草稿"入口多处并存，指向不清

位置：发布页　/build/release
现象
同一页出现多个语义相近的入口：黄条里的"创建草稿"、候选卡的"导入草稿"、次级版本动作里的"派生可编辑草稿"。用户难判断该用哪个、彼此差异是什么。
前端建议
明确区分"从 live 派生草稿"与"导入 package"两条路径，各保留一个主 CTA 并配一句话说明；移除冗余按钮，避免三处都像主操作。
评级
中　工作量：小

U4. 面向用户的文案暴露后端 API 路径

位置：试点实验室 → 应用草稿说明
现象
说明文字写道："这里的 Apply 只会调用 /api/admin/config-pilot/apply，写入 draft 配置…"。把内部接口路径直接展示给操作人员，属实现细节泄漏。
前端建议
改为业务语言描述行为与边界（"应用后会写入草稿配置并将验证标记为过期；发布、激活、回滚不在此处执行"），删除 API 路径。
评级
低　工作量：小

U5. 状态徽章语义与可点性模糊

位置：试点实验室、发布页
现象
"自上次验证后已变更"做成药丸状、看着像按钮其实是状态；旁边"就绪"是极小灰字；绿点/"运行时已验证"/"尚未验证"等状态散落且视觉权重不一，难一眼判断当前处于哪一步。
前端建议
建立统一的状态徽章组件（颜色映射：绿=已验证/live、黄=待验证/已变更、灰=暂无），状态不可点，可点操作用真正的按钮样式区分；在显眼处给一个"当前阶段"指示，串起 草稿→验证→发布。
评级
中　工作量：小–中

五、视觉与加载态

V1. 左上 Logo 裁切/重叠

位置：多页（加载或特定宽度时）
现象
侧栏顶部"intera"logo 多次出现字母被裁切、与"收起侧栏"按钮重叠的情况（如显示成"int e"）。

检查 logo 容器宽度与折叠按钮的定位/层级；给 logo 区固定最小宽度，按钮用 flex-shrink:0，避免重叠；加载完成前用占位避免抖动。
评级
低　工作量：小

V2. 加载态简陋

位置：切换 Agent、进入发布页等
现象
切换 Agent 或进入发布页时，整页只有一个小"正在加载发布控制台…"卡片浮在大片空白中，侧栏 logo 区为空白骨架，过渡突兀。
前端建议
用布局级 skeleton（保留侧栏、卡片轮廓的骨架屏）替代居中小卡片；侧栏 logo/agent 区给固定骨架，减少跳动。
评级
低　工作量：小

六、实操 CRUD：深层交互发现

为了不停留在静态页面，我在 J1B 实际走了一遍"新建 → 编辑 → 保存 → 删除"的完整流程（新建了一个测试 Procedure「ZZ 测试流程-待删除」）。以下是只有动手操作才会暴露的问题，以及几处做得好的地方。

C1. 新建即生成时间戳 slug，并全程暴露给用户

位置：组件 → 流程 →「新建 Procedure type」
现象
点击"新建"不先询问名称，直接创建一条 Procedure，code name 自动取了 new_procedure_1781591946733（时间戳 slug）。该 slug 出现在标识 chip、URL、甚至删除确认文案里；改了"显示名称"后，code name 不会随之生成可读 slug，需要手动改、否则永远是这串时间戳。
影响
机器 slug 对配置人员无意义、难检索；容易留下一堆 new_procedure_… 命名的条目。
前端建议
① 新建时弹轻量对话先收集"显示名称"，由它 slugify 生成 code name（如 account_status）并允许编辑、做唯一性校验；② 或保持即时创建但在保存前用名称回填 slug；③ 删除确认等文案改用显示名。
评级
中　工作量：小–中

C2. 保存无必填校验，可存下"无名"Procedure

位置：Procedure 编辑器
现象
把"显示名称"清空后，保存按钮依然可点、也确实保存成功，没有任何内联报错或拦截。结果会生成一个标题为空（仅显示灰色占位"新建 Procedure"）的 Procedure。
影响
数据完整性风险：列表里会出现"无名"条目，难以辨认与维护；下游引用该 Procedure 时也会混乱。
前端建议
① 对必填项（显示名称、code name）做校验：为空时禁用保存并显示内联错误（红框 + 提示）；② 提交时统一用表单校验库（如 react-hook-form + zod）做 schema 校验；③ 对 code name 限制字符集与唯一性。
评级
高　工作量：小

C3. 保存反馈弱，且顶部状态徽章三重冗余

位置：Procedure 编辑器顶栏
现象
保存成功没有 toast/明确提示，只能靠顶部徽章变化察觉；而保存后顶栏同时出现三个徽章：草稿、已保存、✓已保存——后两个文字重复。"草稿"与"已保存"并存，也让人不确定当前到底是已保存还是仍是草稿。
影响
既缺正反馈（不确定有没有存上），又有冗余噪音，状态语义模糊。
前端建议
① 保存成功给一个轻量 toast（"已保存"）；② 顶部只保留一个状态徽章，按状态机切换：草稿·未保存 / 草稿·已保存 / 已发布；③ 合并重复的"已保存"指示。
评级
中　工作量：小
做得好的地方（保留）：① 编辑器内删除有二次确认弹窗（"删除 Procedure type? 这会永久删除…"，取消/删除分明）；② dirty-state 检测准确——一编辑立即变为"有未保存改动"并点亮保存按钮，离开有据可依；③ 创建后即时进入编辑器、URL 同步，流程连贯。
小瑕疵：删除确认文案用的是 slug new_procedure_1781591946733 而非显示名，建议改用可读名称以防误删；另需确认列表卡片上的"Delete"是否也有同样的二次确认（编辑器内已有，列表卡需保持一致）。

七、优先级建议（落地顺序）

优先问题类型工作量
P0B1 图标名以文本渲染并遮挡标题Bug小
P0B2 i18n key 泄漏Bug小
P1L1 中英混杂 + 组织页重复英文导航本地化中
P1A1 Pilot 右栏过载 / 手写 JSON架构中–大
P1L2 同功能多名（交接/接管）本地化小
P1C2 保存无必填校验，可存"无名"ProcedureCRUD/数据小
P2C1 新建即生成时间戳 slug、C3 保存反馈弱+状态徽章冗余CRUD小–中
P2A2 组件表格重复文案、A3 主区留白、U1 删除防护、U3 草稿入口、U5 状态徽章可用性小–中
